## What this report is, and is not

- Every number below is a real measurement against a live, disposable stack
  on this development machine -- real HTTP calls (`tools/perf_report.py`,
  `tools/perf_upload.py`), a real browser (`apps/dashboard/e2e/perf-dashboard.mjs`),
  and a real bandwidth-capped loopback proxy (`tools/p8_network_proxy.py`).
  None of it is synthetic, mocked, or estimated.
- They measure *this machine's* performance, not a production server's. They are
  useful for regression tracking (did a change make this materially slower?), not
  for capacity planning on unknown target hardware.
- Android on-device assistance timing is **not re-measured here** -- the existing,
  real, dated OnePlus 13R benchmarks already in this repository
  (`docs/evidence/Q2_Q3/oneplus13r-benchmark-final.json`, recorded 2026-10-15/16)

  hardware; no entry/mid-tier measurement; Q3 decoder-fix timing documented there).

## 0. Error-handling fix (this pass)

Both `tools/perf_report.py` and the new `tools/perf_upload.py` previously had
two real bugs, fixed and regression-tested this pass (`tools/tests/`):

1. **An unreachable server or an unimported pack used to crash the whole
   script** with a raw traceback and zero output, discarding any results
   already collected (e.g. a working login measurement, lost because the
   pack lookup that ran right after it failed). Fixed: every connection-level
   failure (`urllib.error.URLError` -- refused/reset/DNS/timeout) and every
   HTTP error response is now captured as a normal, reportable outcome;
   a stage whose prerequisite failed is marked `"status": "skipped"` with an
   explicit `skip_reason`, and every stage already completed is still
   written to `--out`.
2. **`queue_retrieval` and `rubric_retrieval` never checked the HTTP status
   at all** -- they just timed the call and reported success as soon as
   `client.call()` returned *anything*, including a 500 or 403. An error
   response that happened to come back quickly was silently counted as a
   fast successful observation. Fixed: every call site now routes through a
   shared `expect()` helper that raises (and gets recorded as a failure,
   not a success) on any unexpected status.

Both fixes are exercised by `tools/tests/test_perf_report.py` and
`tools/tests/test_perf_upload.py` (18 tests total, mocked HTTP, no live stack
needed, run in CI's `tools-tests` job) and were additionally verified against
a real live stack during this pass: a genuinely unimported pack, a genuinely
stopped API container, a real 500, and a real full success path were each
exercised by hand and confirmed to produce the correct, non-crashing JSON
shape (see the commit history / session evidence for the exact transcripts).

## 3. Throttled upload (real, corrected)

**Unit correction**: an earlier revision of this report configured the proxy
at 262,144 bytes/s and called that "256 kbps". That is wrong: the master
plan's target is in kbps (**kilo*bits***/second, decimal telecom convention,
1 kbps = 1000 bits/s), so 256 kbps = 256,000 bits/s = **32,000 bytes/s** --
not 256 *KiB*/s (262,144 bytes/s), which is ~8.2x faster than intended. The
earlier 262,144 bytes/s run is kept as `perf-upload-throttled-256kibs-2026-10-17.json`
for the record, but it does not satisfy the original requirement; the table
below is the corrected, authoritative measurement.

Fixed as part of the correction: `tools/p8_network_proxy.py` previously
enforced a hard floor of 262,144 bytes/s, which made 32,000 bytes/s
inexpressible even once the unit mistake was caught. It now accepts
`--upload-kbps` directly (so the rate is given the same way the master plan
states it, removing the conversion step that caused the original error) and
its floor was lowered to 8,192 bytes/s.

Source: `docs/evidence/P10/perf-upload-throttled-256kbps-corrected-2026-10-17.json`
and `perf-upload-unthrottled-comparison-2026-10-17.json`. Uses
`tools/p8_network_proxy.py`'s loopback bandwidth cap in front of the real
P8-integration test stack (`infra/docker-compose.p8-test.yml`, API on port
18008), with `tools/perf_upload.py` driven straight through it:

```sh
python3 tools/p8_network_proxy.py --upload-kbps 256 &
server/.venv/bin/python tools/perf_upload.py --base-url http://127.0.0.1:18009 \
  --repeat 2 --photo-bytes 1048576 --video-bytes 0 --chunk-bytes 262144 \
  --out docs/evidence/P10/perf-upload-throttled-256kbps-corrected-2026-10-17.json
# unthrottled comparison, same payload, direct to the same stack:
server/.venv/bin/python tools/perf_upload.py --base-url http://127.0.0.1:18008 \
  --repeat 2 --photo-bytes 1048576 --video-bytes 0 --chunk-bytes 262144 \
  --out docs/evidence/P10/perf-upload-unthrottled-comparison-2026-10-17.json
```

| Condition | 1 MiB photo upload+verify (median) |
|---|---:|
| Unthrottled (direct, same stack) | 107.3 ms |
| Throttled at the correct 256 kbps (32,000 bytes/s) | 32,997.1 ms |

32,997 ms for 1,048,576 bytes at a 32,000 bytes/s cap is within 0.7% of the
theoretical 32,768 ms floor (1,048,576 / 32,000) -- the tiny difference is
real protocol overhead (session open, 4 sequential chunk PUTs,
complete/verify) on top of the raw bandwidth limit, confirming the throttle
now runs at the rate it claims and matches the originally-specified target.
