# Signed on-device assistance contract — version 1

P8 evolves the reserved `EvidenceItem.quality_check_status` contract. Inference runs
only on Android, through the existing Q2/Q3 libraries. No backend AI service or inference
job was added. Advisory findings never feed scoring, outcomes, reassessment or reports.

`contracts/flags.schema.json` is generated by `tools/export_flags_schema.py` from the
strict Pydantic models in `server/app/assistance.py`. Kotlin serializable equivalents
live in `core:seal/AssistanceSnapshot.kt`. Shared privacy-safe fixtures under
`contracts/fixtures/` round-trip through Kotlin, JSON Schema and Python tests. JSON Schema
validates shape; the typed validators also enforce cross-field semantics and binding.

## Envelope and identity

Manifest schema **2** may include an `assistance` snapshot on each evidence entry. Schema
1 (including historical manifests that omit the version) remains supported without this
field. Unknown manifest/assistance versions are rejected, without parsing them as version 1.
New nullable fields are omitted from legacy Kotlin items, preserving their canonical bytes.
The server verifies the exact original ECDSA-signed canonical bytes before interpreting flags.
It never re-serializes bytes to verify a signature or re-signs client evidence.

A snapshot binds `assessmentId`, `taskId`, `evidenceId`, `revisionId`, `revisionNumber`,
`mediaSha256` and `durationMs`. New observations must match their manifest entry and active
server revision. Inherited P7 evidence retains its **original** revision and assistance;
its snapshot must equal the already verified evidence's snapshot. Flags cannot be replaced
in a later revision by re-declaring an unchanged evidence ID.

The canonical manifest has a 1,400,000-byte production metadata budget, leaving space
inside P6's unchanged 2 MiB base64/signature envelope ceiling. Excess diagnostics on new
items become a signed `UNAVAILABLE`/`PAYLOAD_LIMIT` snapshot before signing; the same
snapshot is persisted locally. Inherited flags, evidence bytes/hashes and task/120 MB
budgets are unchanged. A single snapshot is limited to 256 distinct flags and 65,536
bytes server-side. The app stores compact intervals, not per-frame metrics or landmarks.

## Lifecycle and meanings

| Wire state | Existing backend status | Meaning at the seal snapshot |
|---|---|---|
| NOT_RUN | not_run | No result for these exact bytes |
| QUEUED | queued | Work was waiting; no negative prediction |
| RUNNING | running | Work was unfinished; no negative prediction |
| COMPLETED | completed | Required components produced results |
| PARTIAL | partial | Usable results with explicitly incomplete coverage or truncated intervals |
| FAILED | failed | Analysis failed; no claim that capture quality was poor |
| UNAVAILABLE | unavailable | Analysis or metadata unavailable; submission can continue |

The database status describes the **signed device snapshot**, not a server queue that will
later fill in the results. Legacy direct uploads remain `not_run`/`assistance=null`.
Authentication uses the existing assessment/evidence API policy and capability/JWT/cookie
checks; no unsigned assistance update endpoint exists.

Quality and hands each carry status, version/hash provenance and coverage. Quality uses
the threshold-profile hash; hands uses both configuration and model hashes. Coverage gives
requested/analysed sample counts, represented duration, and quality motion-pair coverage.
Failed/unavailable components cannot contain successful observations. Quality's optional
`reviewRecommended` is the existing versioned Q2 combined hint; raw technical intervals
remain separate. Hands exposes raw and gap-filled ratios, and markers use the existing
versioned isolated-gap policy. Detection absence does not establish physical absence.

## Flags and time

Allowed types: `DARK`, `OVEREXPOSED`, `BLURRY`, `CAMERA_MOTION`,
`HANDS_NOT_DETECTED`. Severity is always `review`. Photo flags have `startMs=0`,
`endMs=null`; hands/motion video observations require real temporal intervals. Video
intervals are integer source-relative milliseconds, half-open `[startMs,endMs)`, with
`0 <= startMs < endMs <= durationMs`. Intervals represent sampled cells, not exact
continuous event boundaries. Production sampling is unchanged: Q2 1 s anchors plus
125 ms motion partners, Q3 1 fps/640 px. No semantic task-target framing exists.

Photo observed metrics/thresholds are optional finite, nonnegative numbers, not
probabilities. Ratios must be finite in [0,1]; counts, identifiers, hashes, versions,
unknown keys, future versions and payload sizes are validated. Model/threshold
unavailability, sample failure and incomplete temporal coverage have separate meanings.
The libraries' existing 20-minute decoder cap is **not** a new evidence-submission limit:
longer valid media can still carry unavailable/failed analysis.

`durationMs` is device-reported and signed; the server's ffprobe metadata and the browser's
actual playable duration can differ. Signed snapshots are preserved. The dashboard positions
markers using the native player's actual duration, disables markers until that duration is
known, and explicitly explains duration differences. A range that overlaps playable footage
is visually intersected with that footage; the original signed start/end label and source
seek offset remain unchanged. A start at/beyond playback end is disabled and no range is
drawn. No duration is fabricated and no signed metadata is rewritten. This is tested with
a deliberately wholly out-of-range persisted fixture and actual unchanged CameraX bytes:
Android reported 45,058 ms while Chrome reported 45,056.644 ms. No arbitrary timing
tolerance or inference-policy change is used.

## Persistence and sealing

Room v6 adds `evidence_assistance`, foreign-keyed to the evidence row. Generation tokens,
revision numbers, selected media paths and pre/post SHA-256 checks prevent stale writes.
WorkManager has one unique job per item, while a shared semaphore permits one active
native analysis. State/stage/results persist; launch recovery repairs an interrupted enqueue
or work item. Repeated unchanged content does not trigger fresh inference.

P5 optimisation re-schedules changed bytes. Proven byte equality plus equal duration permits
reuse. The transition to `SEAL_IN_PROGRESS` freezes analysis writes. The seal reads and stores
a deterministic snapshot without waiting for inference, then signs/encrypts the existing P5
package. Late workers cannot alter it. P6 verifies signed metadata before accepting evidence
bytes and persists assistance only after matching server-computed hash, size and task binding.
Alembic `b89e72c4d010` adds one nullable JSON column; existing quality status is reused.
