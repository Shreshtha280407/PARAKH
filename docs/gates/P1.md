refuses to run against any dataset carrying the harness marker (verified
above). The 1.000 agreement is a property of the synthetic archetypes, not a
claim about real-world matcher accuracy.

## Known, stated gaps (not blockers for P1 engineering, carried forward openly)

1. `ml/mapping/data/labelled_60.jsonl` is synthetic, not field data —
   structurally enforced by `eval.py --mode harness`/`--mode field`, not just
   documented.
2. `CON/N8001`, `CON/N8002`, `DGT/VSQ/N0101` are not task-evidenced or
   rubric-scored in the MVP (declaration + assessor notes only) — matches
   the master plan's stated scope (p.4-5), not an oversight.
3. `CON/N0603.PC16` (diesel generator preventive maintenance) has no
   declaration card and no real capture step — there's no generator on the
   training board. It carries a `DIRECT_TASK_EVIDENCE` task reference
   (satisfies the "every practical PC has >=1 task" rule) but
   `coverage_matrix.json` flags it with an explicit `caveat` so a future
   assessor doesn't mistake its presence in `rubric.json` for real coverage.
4. Per-PC marks in `rubric.json` are an equal split of each element's
   official marks (the QP publishes per-element, not per-PC, marks) —
   flagged for expert review.
5. Only the pinned `qp_v4.0.pdf` is used anywhere in this pack. Other
   publicly hosted Assistant Electrician documents (older versions, Model
   Curricula, Assessment/Facilitator Guides) were found during sourcing and
   deliberately **not** consulted — see `docs/qp_source_reconciliation.md`.

## Final checklist — two different bars, not one

**P1 engineering completion = all automated checks pass.** This is done:
`pack_validate.py`, `audit_qp_traceability.py`, the matcher self-check, the
golden-vector parity test, and all 5 negative-fixture cases are green (see
the transcript above and the full run in
`docs/P1_TECHNICAL_COMPLETION_REPORT.md`). **This is sufficient to start
P2/P3** — the trade-expert review does not gate engineering work on the
backend, dashboard, or Android app, because those phases build against
`qp.json`/`rubric.json`/`mapping/*.json` as data contracts, not against the
*correctness* of that data's pedagogical judgement calls.

**Pilot readiness** is a separate, later bar: independent field validation
by the trade expert (anchor review, match-rule review against real
declarations, the actual IC-1 ≥90% agreement run with `--mode field` against
real labelled data) **is required before pilot deployment or any claim that
the task realism / rubric / matcher have been validated** — but it does not
block engineering work on P2/P3. Treat the two "not done" checkboxes above
as a pilot-readiness blocker, not an engineering blocker.
