### A real cross-language float-summation bug, found and fixed during Kotlin porting

Porting the matcher to Kotlin (`docs/gates/P3.md`) surfaced a genuine
Python/Kotlin parity bug, not a porting typo: CPython's builtin `sum()` has
used Neumaier (compensated) summation for float addition since Python 3.12,
which is measurably more accurate than naive sequential `total += v`.
Kotlin's stdlib `Iterable<Double>.sum()` is naive. For most declarations the
one-ULP difference this produces is invisible after rounding to 4 decimal
places — but for a PC-coverage value landing exactly on a rounding boundary
(`0.225 × 3 ÷ 12 = 0.05625`, a true half-way point at 4 decimals), naive
summation in one language and compensated summation in the other can round
to *different* 4th decimal digits (`0.0562` vs `0.0563`). This is exactly
the kind of silent, hard-to-spot discrepancy the "100 golden vectors must
match exactly" requirement exists to catch.

Fix: `ml/mapping/matcher.py` now has an explicit, auditable
`_compensated_sum()` (standard Neumaier algorithm) used everywhere the
matcher sums floats, replacing calls to the builtin `sum()`. The Kotlin port
(`core:mapping`'s `Matcher.kt`) implements the identical algorithm as
`compensatedSum()`. Both languages now depend on the same hand-written code,
not on a Python-version-specific standard-library implementation detail.
Also fixed in the same pass: per-NOS PC iteration now sorts PC ids before
summing their claims (`sorted(nos_pcs.get(nos, set()))` in Python,
`.sorted()` in Kotlin) — Python's native `set` iteration order is
hash-seed-dependent (hash randomization has been on by default since Python
3.3), so without sorting, `matcher.py` was not even deterministic *across
separate Python process runs*, let alone identical to Kotlin's
insertion-ordered `LinkedHashSet`. Verified with
`PYTHONHASHSEED=1` vs `PYTHONHASHSEED=42` producing byte-identical output.
All 100 golden vectors were regenerated after this fix; the fix did not
change any vector's `match_result`, only a handful of `because`-line `.2f`
displays and 4th-decimal `overall_coverage` digits at exact rounding
boundaries.

## Validation suite (robust input handling)

`ml/mapping/matcher.py`'s `normalize_declaration()` / `validate_declaration()`
and 7 tests in `test_matcher.py` cover what the 100-vector success-path
contract structurally cannot (a `ValueError` has no `expected_output` to
pin):

- Unknown declaration item id → `ValueError` naming the id
- Unsupported claim-strength value (anything other than
  `often`/`sometimes`/`never`) → `ValueError` naming the id and value
- Duplicate `item_id` in the list-keyed input form → `ValueError`
- Non-object declaration, non-object/non-list `answers`, non-string
  `free_text` → `ValueError`
- List-keyed input normalizes to the identical result as dict-keyed input
  for the same data
- Missing `answers`/`free_text` keys default to empty, not an error

## EN/HI/Hinglish free-text support

`packs/ae-con-q0602/mapping/keywords.json` carries `en`/`hi`/`hinglish`
keyword lists per card (51 cards now, up from 35 at r1 — includes the 8 new
safety cards and 8 new teamwork/planning cards). Matching is deterministic
case-insensitive substring matching on normalised (trimmed, lowercased)
text — no NLP model, no network call, no translation API. A keyword hit
raises a `never`/unanswered card to `sometimes` (0.6); it **never** lowers
an existing `often` answer — verified by
`test_matcher.py::test_free_text_never_overrides_structured_often`.
Dedicated tests: `test_hindi_keyword_boosts_coverage`,
`test_hinglish_keyword_boosts_coverage`. Golden-vector coverage: `G018`-`G020`
(Hindi), `G021`-`G023` (Hinglish), plus Hindi/Hinglish phrases already
embedded in several of the seeded mixed-random vectors' free text.

## Honest internal validation data

`ml/mapping/data/labelled_60.jsonl` is regenerated by
`ml/mapping/generate_labelled_60.py` — three synthetic archetypes
(experienced / partial / unrelated), 20 records each, `expected_match`
assigned **by archetype design**, not computed from `matcher.match()` (so
the agreement number stays a real check, not a circular one). Every record
carries `"harness_marker": "HARNESS_ONLY_NOT_FIELD_VALIDATION"`. It is
never referred to as expert-labelled or field-validated anywhere in this
repo — `eval.py --mode field` mechanically refuses to run against it.
