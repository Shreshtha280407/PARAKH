## Scope and the P6 boundary

**In scope, implemented and verified below:** automatic local photo/video optimisation that
fits captured evidence to the real T1-T5/120 MB final-package budgets without ever exposing a
bitrate/resolution/JPEG-quality/file-size control to the worker; a pure, exhaustively-tested
deterministic budget ledger; a worker-facing final-review/seal screen with per-item
optimisation status, retake/replace/delete/trim access, and a required attestation; a
canonical, deterministically-serialised manifest; streaming SHA-256 of every final file;
Android Keystore ECDSA (SHA256withECDSA) signing with a non-exportable key; a Tink
StreamingAead-encrypted local vault with per-item associated-data binding; a durable Room
outbox in state `READY_TO_SYNC`; a crash-safe `DRAFT_EDITABLE -> ... -> READY_TO_SYNC` state
machine; a debug-only `P5_TEST_ONLY` forced-budget optimiser test mode and a debug-only
decrypt-for-verification export, both genuinely absent from release build output (not merely
runtime-disabled); and the two mandatory P4 closure corrections.

**Explicitly out of scope, not implemented, not claimed as implemented:** P6. No HTTP call,
no WorkManager upload worker, no polling, no server receipt handling, no deletion-after-upload
logic exists anywhere in this codebase. No assessor workflow, no CV/AI inference, no quality
flags, no dashboard change, no report, no reassessment flow, no automatic competence decision,
and no "certified"/"passed" wording anywhere in P5's UI strings. `android.permission.INTERNET`
is not declared; `android.permission.ACCESS_NETWORK_STATE` is both not declared directly and
explicitly stripped (`tools:node="remove"`) from the real merged manifest where a dependency
(Media3's ExoPlayer, pulled in transitively for real local Transformer video processing) would
otherwise have injected it — see "A real regression this phase found and fixed" below. The
sealed package sitting in `READY_TO_SYNC` is the complete contract P6 will consume; nothing
about *how* P6 uploads it was built or assumed here.

## Module architecture

```
core:budget   -- pure Kotlin/JVM, no Android dependency. BudgetLedger: recomputes task/total
                 usage, allowed-bytes, accept/fit decisions purely from a source-of-truth
                 LedgerItem list passed in on every call -- never a cached/incremental total.
media         -- Android library. PhotoOptimizer (real BitmapFactory/Bitmap, RAM-safe
                 inSampleSize decode), VideoTranscodePlanner (pure bitrate/resolution
                 planning), VideoOptimizer (real Media3 Transformer: optimise + trim).
core:seal     -- Android library. StreamingHasher (SHA-256, 64 KB chunks), SealManifest /
                 SignedManifestPackage (canonical JSON), ManifestSigner (Keystore ECDSA
                 sign + pure verify), VaultStreamCipher / VaultCipher / VaultKeysetProvider
                 (Tink StreamingAead, Keystore-protected keyset -- Tink types never leak
                 past this module's own VaultCipher wrapper).
app           -- Compose UI, Room (P4 draft schema extended to v3), SealOrchestrator (the
                 one place core:budget + media + core:seal + Room are tied together and the
                 SealState state machine's crash-safe transitions live).
```

`SealOrchestrator` (`app/src/main/kotlin/in/kaushalpramaan/app/data/seal/SealOrchestrator.kt`)
is the single orchestration point, mirroring P4's `EvidenceRepository` pattern: UI code never
touches `core:budget`/`media`/`core:seal` directly.

### State machine

```
DRAFT_EDITABLE --processEvidence()--> PROCESSING --(all fit)--> FINAL_REVIEW_READY
FINAL_REVIEW_READY --(any item QUALITY_FLOOR_EXCEEDED)--> DRAFT_EDITABLE
FINAL_REVIEW_READY --seal(), attested--> SEAL_IN_PROGRESS --> VAULT_READY --> READY_TO_SYNC
any state --discardAndReopen()--> DRAFT_EDITABLE (restores evidence from the vault first if
                                    the prior state was READY_TO_SYNC -- see below)
```

Per-evidence-item mirror: `FinalEvidenceState { NOT_PROCESSED, FITS_AS_IS, OPTIMIZED,
QUALITY_FLOOR_EXCEEDED, SEALED }`, stored on the same `EvidenceDraftEntity` row P4 already
uses (Room schema v2 -> v3, real additive `MIGRATION_2_3`, never
`fallbackToDestructiveMigration`).

**Crash recovery** (`SealOrchestrator.reconcileOnLaunch`, called once per process start):
- `PROCESSING` resumes by re-running `processEvidence()` — idempotent per item (an item whose
  `finalState != NOT_PROCESSED` is skipped), so an interrupted optimisation pass picks up
  exactly where it left off, never reprocessing already-finished work, never losing an item.
- `SEAL_IN_PROGRESS` / `VAULT_READY` with **no committed outbox rows** for the current
  revision rolls back: the partial vault directory is deleted and `sealState` returns to
  `FINAL_REVIEW_READY` — a partially-encrypted package is never exposed as `READY_TO_SYNC`.
- `SEAL_IN_PROGRESS` / `VAULT_READY` with a **committed outbox** (proof the vault work
  genuinely finished before the crash) finishes the tail idempotently: marks every item
  `SEALED`, deletes plaintext, sets `READY_TO_SYNC`.

All three branches are exercised by real, passing tests — `SealOrchestratorTest`
(Robolectric, the two PROCESSING/rollback branches) and
`SealOrchestratorInstrumentedTest`/manual gate Group 7 (the real-Keystore/Tink-dependent
committed-outbox branch and a real reboot).

**Discard/reopen** (spec E.4, the only path back to editing): deletes the outbox rows and
vault directory for the current revision, resets every item to `NOT_PROCESSED`, clears
attestation, and generates a fresh `revisionId`. If the assessment had already reached
`READY_TO_SYNC` (meaning P4's raw plaintext was already deleted per G.5), it first **decrypts
every item back from the vault** to its original `relativePath`, using the *old* revisionId's
associated data, before any of that cleanup runs — verified byte-identical to the original
capture by `SealOrchestratorInstrumentedTest.discard_and_reopen_after_a_real_seal_restores_
evidence_by_decrypting_the_real_vault`. Evidence is never silently lost by a discard.

## Photo optimisation rules (spec part C)

1. `PhotoOptimizer.validateDecodable` — bounds-only decode (`inJustDecodeBounds`), safe on
   arbitrarily large/corrupt files.
2. Already fits the target: returned **byte-identical**, same `File`, never recompressed.
3. Does not fit: decode with a computed `inSampleSize` (never full-resolution unless
   necessary), resize longest side to at most **1600px**, try JPEG quality **85**, then the
   **75** floor; orientation is baked into pixels via the EXIF rotation/flip matrix (never
   left to a downstream EXIF reader) before encoding.
4. Still does not fit at the floor: the floor-quality attempt is **kept on disk**, not
   deleted — `FinalEvidenceState.QUALITY_FLOOR_EXCEEDED`, surfaced to the worker with a
   retake/replace/remove message; never silently destroyed.
5. Real tests: `PhotoOptimizerTest` (12/12) — byte-identical fit, real resize/quality ladder,
   quality-85-before-75, orientation (pixel-matrix rotation + EXIF-tag reading, split to avoid
   a real Robolectric native-codec limitation re-decoding an `ExifInterface`-rewritten JPEG —
   documented in the test file, not a production-code issue), quality-floor refusal keeps a
   decodable draft and cleans up the rejected intermediate attempt, undecodable-input safety.

## Video optimisation rules (spec part D)

1. `VideoOptimizer.validateContainer` — `MediaMetadataRetriever` metadata only, never decodes
   frame data.
2. Already fits: returned **byte-identical**.
3. Does not fit: **one** planned pass via `VideoTranscodePlanner` — bitrate reduced first;
   resolution only steps HD (1280×720) down to SD (854×480) once bitrate reduction alone at
   the source's own tier would cross below that tier's documented quality floor
   (`MIN_VIDEO_BITRATE_BPS_HD` = 1.2 Mbps, `MIN_VIDEO_BITRATE_BPS_SD` = 0.6 Mbps). Output is
   always H.264/AAC in MP4, encoded with `BITRATE_MODE_CBR` explicitly requested. File-to-file
   via the real Media3 `Transformer`; no video frame data is ever loaded into the JVM heap.
4. Still does not fit: the SD/floor attempt is **kept on disk**, not deleted —
   `QUALITY_FLOOR_EXCEEDED`, same honest never-destroy guarantee as photos.
5. Minimal trim (`VideoOptimizer.trim`): start/end only, no quality control, via Media3's
   `MediaItem.ClippingConfiguration`; re-validated and re-optimised through the exact same
   pipeline afterward (trim never bypasses the budget ledger); the pre-trim clip is left
   completely untouched unless the trim genuinely succeeds.
6. Debug-only `P5_TEST_ONLY` forced-budget test mode (`BuildConfig
   .P5_TEST_ONLY_FORCE_OPTIMIZE_ENABLED`, compile-time `false` in release, verified below):
   substitutes a smaller **total** budget into the exact same `BudgetLedger`/optimiser call —
   never a separate mock path. This exists because real per-task budgets (15-30 MB) comfortably
   exceed a typical real phone photo/video, and P4's own fail-closed capture-time check (just
   fixed in the P4 closure pass above) already guarantees every item fits those real budgets by
   the time P5 ever sees it — so in ordinary use the "needs optimisation" branch is naturally
   rare. The debug override is the intended, honest way to exercise the real optimiser path
   against a real capture, both in automated tests and in the manual gate below.
7. **A real, documented, measured correction made during this phase:** real Media3 hardware
   encoding on the OnePlus 13R did not respect a bare requested bitrate closely even with
   `BITRATE_MODE_CBR` set — observed overshoot of roughly 1.3-1.4x (with CBR) and up to 2.3x
   (without) versus the requested value for a short clip. `VideoTranscodePlanner
   .CONTAINER_OVERHEAD_SAFETY_FACTOR` was tightened from an initial 0.95 to **0.6** in response
   to this real measurement so the planned pass reliably lands under budget on real hardware;
   `VideoOptimizer.optimize` still verifies the real output size afterward regardless and
   reports `QUALITY_FLOOR_EXCEEDED` rather than ever adopting an over-budget result, so this
   margin is a quality-of-fit tuning, not the actual safety guarantee.
8. Real tests: `VideoTranscodePlannerTest` (7/7, pure, bitrate-before-resolution, planned
   bitrate × duration respects budget, impossible-target floor estimate) and
   `VideoOptimizerInstrumentedTest` (6/6, **real device**, real Media3 Transformer: byte-
   identical fit, a real transcode that genuinely shrinks and fits, a real floor-quality
   recoverable draft, invalid-container safety).

## Budget ledger (spec part B)

`BudgetLedger` (`core:budget`) is pure and holds no state: `usage()`, `allowedBytesFor()`,
`canAccept()`, and `fitDecision()` all recompute from a `List<LedgerItem>` the caller passes in
— always the real current READY-evidence set, never a cache. `SealOrchestrator.processEvidence`
processes items in a stable order (task id, then capture time), each one's `allowedBytesFor`
computed from every *other* item's current final-or-raw bytes, so later items correctly see a
shrinking budget as earlier ones claim their share.

`BudgetLedgerTest` (12/12) includes the required **500-randomized-operation** invariant stress
test: a simulated add/replace/delete/recompute-after-crash sequence (seeded, reproducible),
asserting after **every single operation** that no task and no total ever exceeds its budget,
plus a second 500-operation run asserting no duplicate/dangling evidence id ever appears.

## Canonical manifest, hashing, signing (spec part F)

`SealManifest` (`core:seal`) carries: schema version; assessment/revision id; QP code and
pinned QP version (also standing in for the task-pack/rubric/mapping version identifiers — the
app has no separate version field for those beyond the one pack version `core:mapping`'s
`Rules`/`TasksFile` already expose; a deliberate choice not to invent fields with no real
source of truth); app version; created/sealed timestamps; attestation state and timestamp;
every final evidence item (opaque id, task id, kind, final filename, exact bytes, SHA-256,
MIME type, duration/resolution where available, and a `processing` field naming exactly how it
was produced — `FITS_AS_IS`/`OPTIMIZED`/`QUALITY_FLOOR_EXCEEDED`/`SEALED`); per-task and
assessment final totals; a stable `idempotencyKey` (`"<assessmentId>:<revisionId>"`) for P6;
and the signer's key id and public key material.

`canonicalJsonBytes()` sorts the `evidence`/`taskTotals` lists by their own id (so caller
construction order never affects the signed bytes) and serialises via `kotlinx.serialization`
in this class's fixed declaration order, compact (no pretty-printing), UTF-8 —
`SealManifestTest` proves this is order-independent and repeatable for identical content.

Every final plaintext file is hashed via `StreamingHasher.sha256Hex` — a 64 KB buffered read
loop, proven stable across buffer-boundary-sized files, never a whole-file read into memory.

`ManifestSigner.getOrCreateSigningKey` generates (once, idempotently) a **non-exportable** EC
(`secp256r1`) key directly inside the Android Keystore; `sign` uses `SHA256withECDSA`; `verify`
is pure and works against any EC public key, so it is unit-tested with a software key
(`ManifestSignerTest`, 5/5: untouched verifies, one-byte manifest tamper fails, one-byte
signature tamper fails, wrong public key fails, garbage signature never throws) while the real
Keystore-backed key generation/signing/non-exportability is proven on the real device
(`ManifestSignerInstrumentedTest`, 4/4).

## Encrypted vault and outbox (spec part G)

`VaultKeysetProvider.getOrCreateCipher()` returns a `VaultCipher` wrapping a Tink
`StreamingAead` primitive whose keyset is protected by an Android Keystore-backed master key
via `AndroidKeysetManager` (Tink's own recommended production pattern) — the raw keyset is
never held, logged, or exportable in plaintext; `VaultCipher`/`VaultStreamCipher` are the only
public surface (the Tink `StreamingAead` type itself never leaks past `core:seal`'s module
boundary, keeping `:app` free of a direct Tink dependency for anything but the shared manifest
model). `associatedData(assessmentId, revisionId, evidenceId, role)` binds every ciphertext to
exactly the item/assessment/revision it belongs to — `VaultStreamCipherTest` (5/5, software
test keyset) proves encrypt/decrypt round-trips exactly, ciphertext never contains the
plaintext header, decryption fails on AAD mismatch (the swap-rejection case), on the wrong
keyset, and after a one-byte ciphertext tamper; `SealOrchestratorInstrumentedTest
.tampering_with_a_copied_vault_file_breaks_decryption...` repeats the tamper proof against the
**real** production Keystore-backed keyset.

`seal()` writes one `manifest.vault` (a `SignedManifestPackage` — canonical bytes + signature +
algorithm + key id + public key, base64-wrapped in one small JSON envelope) and one
`<evidenceId>.vault` per final item, all in `files/vault/<assessmentId>/<revisionId>/`, then
commits Room `outbox_items` rows: the manifest first (`priority = 0`), each evidence item after
(`priority >= 1`), `idempotencyKey` shared across the revision, retry-metadata columns
(`retryCount`, `lastAttemptAtMillis`) present as placeholders P5 never reads or writes beyond
their zero/null defaults — P6's eventual job, not P5's. Only **after** the outbox is committed
does `finishSealAfterOutboxCommitted` mark every item `SEALED` and delete the plaintext raw
capture and any optimisation temp file — `SealOrchestratorInstrumentedTest
.full_real_seal_produces_a_real_keystore_signature_and_a_real_encrypted_vault_with_committed_
outbox` proves all of this for real: a real signature, real non-plaintext vault files (no JPEG
magic header), a correctly-ordered two-row outbox, and a clean plaintext sweep afterward.

P5 performs **no** HTTP call, no `WorkManager` upload worker, no polling, no server receipt
handling anywhere in this codebase — confirmed by the unchanged `verifyNoNetworkDependencies`/
`verifyMergedManifestHasNoNetworkPermissions` gates (see below) and a manual `grep` of this
phase's diff for `HttpURLConnection`/`OkHttp`/`WorkManager`/`Retrofit`, all absent.

## A real regression this phase found and fixed

Pulling in Media3 Transformer (`media3-exoplayer`/`media3-common`) for real local video
processing transitively injected `android.permission.ACCESS_NETWORK_STATE` into the **merged**
manifest via those libraries' own manifests (for ExoPlayer's network-playback features, which
this app never uses) — invisible to the existing `verifyNoNetworkDependencies` task, which only
ever scanned this module's own manifest *source* file. This was caught by a real
`connectedDebugAndroidTest` failure (`SqlCipherAndPermissionsTest
.app_has_no_internet_and_no_network_state_permission`), not by any static check, during this
phase's own regression pass. Fixed two ways: (1) `app/src/main/AndroidManifest.xml` now
explicitly declares `<uses-permission android:name="android.permission.ACCESS_NETWORK_STATE"
tools:node="remove" />`, stripping it back out during Android's manifest merge regardless of
which dependency injects it; (2) a new `verifyMergedManifestHasNoNetworkPermissions` Gradle
task inspects the real merged manifest for both build variants (not just the source file) so
this exact class of regression cannot silently recur. Re-verified: the real merged manifest for
both debug and release now contains `CAMERA`, `RECORD_AUDIO`,
`DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION` (harmless, self-scoped), and `WAKE_LOCK` (legitimate,
benign — lets real video processing keep the CPU awake during a transform; not network-related
and not prohibited by this phase's scope) — no `INTERNET`, no `ACCESS_NETWORK_STATE`.

## Final review / seal UI (spec part A)

`PreviewScreen` (reused file, substantially rewritten; its route/behaviour is now the real P5
final-review-and-seal screen, no longer the P3 placeholder) shows, per task: each final item's
kind icon, current effective byte size (final once processed, raw otherwise — computed live
from the real evidence rows, never a stale P4-era cached `TaskDraftEntity.capturedBytes` sum,
which would otherwise go stale the instant P5 optimisation changes an item's effective size;
see `AppUiState.taskEvidenceBytes`'s doc comment for the real bug this fixes), its optimisation
status, a "View" action (into the existing `EvidencePreviewScreen`, itself now gated so
retake/delete only render in `DRAFT_EDITABLE`), and a "Trim" action for video. Per-task and
total MB progress bars. An "Optimize evidence" button drives `processEvidence()`; on success,
"Evidence optimized successfully. Final size: XX MB. Review the evidence before submitting." is
shown; if any item cannot fit, a clear budget-exceeded message is shown instead. The
attestation checkbox ("I confirm this evidence shows my own work.") is disabled until every
item is processed and none exceeds budget. "Seal assessment" is disabled until
`sealState == FINAL_REVIEW_READY` **and** attestation is confirmed. No bitrate/resolution/
JPEG-quality/file-size control is exposed anywhere. After a real seal, "Assessment sealed on
this device. Ready to sync when connectivity is available." is shown, plus an explicit
"Discard seal and edit evidence" action (confirmation-gated). No "certified"/"passed"/automatic
competence-decision wording appears anywhere in this phase's strings (English or Hindi).

## Debug-only verification export (spec part H)

`DebugExportHooks` (interface + plain data classes only) lives in the shared `app/src/main`
source set; its real decrypting implementation (`RealDebugExportHooks`) lives **only** in
`app/src/debug` — genuinely absent from a release build's compiled output, not merely disabled
by a runtime check. `app/src/release` provides a no-op counterpart with the identical factory
function signature, so AGP compiles exactly one body into any given variant. Verified by a real
Gradle task (`verifyP5DebugExportAbsentFromRelease`, see below) that inspects the actual
compiled `.class` output: `RealDebugExportHooks.class` must exist in the debug build and must
NOT exist in the release build, and release's `NoOpDebugExportHooks.class` must be present
(so the feature is proven correctly variant-split, not silently missing from both). Decrypts a
sealed `READY_TO_SYNC` package's manifest and every evidence item into a fresh app-private
`files/p5_debug_export/<assessmentId>/<timestamp>/` directory, re-verifying the signature and
every item's SHA-256 against the manifest as it goes, with an explicit in-app cleanup action
(`DebugExportHooks.cleanup`) that deletes the whole export tree. Never uses public storage,
Gallery, or a share intent.

- No Gallery import, no Gallery/media-read permission, no `INTERNET`, no real
  `ACCESS_NETWORK_STATE` (see the regression above) — `verifyNoGalleryImportPath`,
  `verifyNoNetworkDependencies`, `verifyMergedManifestHasNoNetworkPermissions` all still green.

  (`files/p5_temp/`), the encrypted vault (`files/vault/`), the debug export
  (`files/p5_debug_export/`) — no public storage, no `MediaStore`, anywhere.

  Backup/device-transfer entirely at the OS level; `data_extraction_rules.xml`/
  `backup_rules.xml`'s explicit excludes remain defense-in-depth documentation of intent on
  top of that, covering the P4 database/passphrase/drafts — P5 adds no new backup-eligible
  path (vault/keysets/debug-export all live under the same already-excluded-by-`allowBackup`
  private storage root).
- Structured log tags: `KP-Seal` (this phase) alongside the existing `KP-Capture`
  (P4, unchanged) — both carry only task/evidence ids, lifecycle-state names, byte counts, and
  error categories; never a file path, media content, hash of private key material, plaintext
  key, or worker data. Grepped this phase's own new/changed `Log.*` call sites by hand to
  confirm.
- `.gitignore` extended for P5 artifacts (`*.vault`, the Tink keyset prefs filename, local test
  signing-key names, a local debug-export staging path) — same "defensive guard against a local
  working copy landing in the repo" reasoning as P4's existing `*.db`/`*.jks` rules; none of
  these ever actually exist inside the repository directory in normal operation (they are all
  app-private on-device paths), this only guards against an accidental `adb pull`.

### Real bugs found and fixed during this gate (not caught by the original automated suite)

1. **Budget double-counting NOT_PROCESSED siblings.** `SealOrchestrator.processEvidence()`'s
   per-item `allowedBytes` calculation counted *every* READY sibling's raw byte size as
   already "used", including items that hadn't even attempted optimisation yet — so the first
   item in a task could see its own budget already exhausted by siblings that hadn't claimed
   anything. User-visible symptom: "its coming too large for the remaining task" even for
   evidence well under budget. Fixed by restricting the "others" set to only
   `FITS_AS_IS`/`OPTIMIZED` siblings — see the code comment and the regression test
   `earlier_items_claiming_budget_does_not_wrongly_zero_out_a_later_items_allowance` in
   `SealOrchestratorTest`.
2. **One failed sibling cascading into blocking every other item.** The first fix still
   counted a `QUALITY_FLOOR_EXCEEDED` sibling's floor-attempt bytes against the budget,
   so one genuinely-too-large item could starve every other item's allowance even though
   sealing was already blocked by that failure regardless. Fixed in the same pass as #1.
3. **Retake/replace/delete/trim hidden after a successful optimisation pass.** The UI gated
   those actions behind `sealState == DRAFT_EDITABLE` only; once optimisation succeeded and
   `sealState` became `FINAL_REVIEW_READY`, the controls silently disappeared even though
   nothing had actually sealed yet. Fixed with a `SealState.isEditable()` extension
   (editable unless `SEAL_IN_PROGRESS`/`VAULT_READY`/`READY_TO_SYNC`) plus
   `SealOrchestrator.invalidateFinalReviewIfNeeded()`, wired into `finalizeCapture()` and
   `deleteEvidence()` so a later edit correctly reverts `FINAL_REVIEW_READY` back to
   `DRAFT_EDITABLE`.
4. **Retake navigation stuck on "Loading" forever.** `AppNavGraph`'s retake handler
   `popUpTo(Routes.TASK_DETAIL)` assumed the evidence-preview screen was always reached via
   task detail, but P5's review screen also opens it directly — when `TASK_DETAIL` wasn't on
   the back stack, nothing popped, and capture's own `onDone = popBackStack()` landed back on
   the stale, now-deleted `evidenceId`, which never resolves. Fixed by popping the preview
   screen itself before navigating to capture, so `onDone` always lands on whichever screen
   actually opened it.
5. **`PreviewScreen`'s sealed branch bounced straight back to the Submitted screen.** A
   `LaunchedEffect(sealed) { if (sealed) onSubmitted() }` fired on first composition too, not
   only on a live state transition — so navigating into the already-sealed review screen (via
   "View sealed evidence") immediately kicked back out. Fixed by removing the `LaunchedEffect`
   and calling `onSubmitted()` directly, once, only from the real seal action's own success
   branch.
6. **`p5_temp` optimisation-scratch files orphaned on assessment deletion.**
   `finishDeletingAssessment()` deleted the `drafts/` tree but never called
   `fileManager.deleteP5TempTree()`, which lives under a separate root — real optimised copies
   of a worker's photos/videos were found surviving indefinitely after their assessment was
   deleted. Fixed by calling `deleteP5TempTree()` from `finishDeletingAssessment()`, plus a
   retroactive sweep in `reconcileOnLaunch()`'s orphan-file pass for any assessment deleted by
   an older build before this fix existed.
7. **`discardAndReopen()` not crash-safe across its restore-then-finish boundary.** The vault
   was decrypted back to plaintext, then — in the same method, no DB write in between — the
   assessment row was flipped to `DRAFT_EDITABLE` and the vault/outbox were destroyed. A
   process death between those steps left the DB still claiming `READY_TO_SYNC` (UI still
   showing "sealed") while a stray *unencrypted* plaintext copy of evidence the app's own
   invariant promises is encrypted-only now sat on disk with nothing to detect or clean it up
   — confirmed live via a real `am force-stop` landing in exactly that window. Fixed by
   splitting the method (`restoreItemsFromVault` / `finishDiscardAfterRestore`), flipping the
   assessment-level DB row to `DRAFT_EDITABLE` as the very first write in the finish step, and
   adding a `reconcileOnLaunch()` case for `READY_TO_SYNC` that detects the exact crash
   signature (plaintext present at an item's `relativePath` while its vault file still also
   exists) and calls `finishDiscardAfterRestore` to complete the transition the user already
   asked for.
8. **Restored evidence left with stale raw-capture metadata.** The vault only ever stores an
   item's *final* (already-optimised) bytes — the raw capture is deleted at seal time — but
   `discardAndReopen()` was restoring those final bytes into the raw-capture file slot while
   leaving `byteSize`/`widthPx`/`heightPx` at their original pre-optimisation values, so the DB
   permanently disagreed with the file actually on disk after any discard/reopen following a
   real optimisation pass. Fixed by promoting the final metadata onto the base fields when
   restoring a genuinely-sealed item. Covered by the new instrumented test
   `discard_and_reopen_after_a_seal_that_actually_optimised_restores_matching_metadata` in
   `SealOrchestratorInstrumentedTest`, which forces real compression via a tiny debug budget
   override and asserts the restored file's actual on-disk length matches the DB row.

All eight are genuinely fixed in this branch, covered either by an existing/new automated
regression test or by live re-verification (or both), and were not worked around, deferred, or
silently reverted.
