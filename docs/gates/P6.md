# P-6 gate — resumable sync and assessor review

Phase owner: this completion pass. Window: 2026-10-12 to 2026-10-13. Branch:
`feature/p6-resumable-sync-review`, based on `origin/main` at
`21d3911a4752bf6ff86dff6318b72b648f2b81e7` (merged P5, PR #6).

## Scope and the P7/P8/P9 boundary

**In scope, implemented and verified below:** a real WorkManager-driven resumable sync
layer that consumes P5's existing `READY_TO_SYNC` encrypted outbox and uploads it to the
FastAPI backend in 1 MiB plaintext chunks over HTTPS, streamed directly from the Tink vault
(never decrypted to disk, never loaded whole into memory); a server-side protocol that
begins/recovers upload sessions for both the P5 signed manifest and each evidence item,
cryptographically verifies the manifest's Android Keystore ECDSA signature, cross-checks
every uploaded evidence item's hash/size/task-binding against that verified manifest, pins
the signing device's public key on first contact (TOFU) and rejects any later revision
signed by a different key, handles revision supersession (a discard/reopen on the phone
produces a fresh revision; an older one's in-flight uploads are rejected), and only then lets
the assessment move out of `draft`; a background worker job that extracts real
width/height/duration metadata via `ffprobe` (alongside the pre-existing `verify_evidence`
hash recheck and `generate_thumbnail` jobs); a functional assessor review workspace (queue →
assessment detail → declaration/QP-match summary → sync/package-integrity status → protected
evidence gallery/player with task tabs → PC scoring → audit log); a worker self-registration
bootstrap endpoint and a QP pack lookup endpoint (both newly required once the phone needs to
talk to a server it has never contacted before); and full automated test coverage (Android
unit + instrumented, backend pytest against real PostgreSQL, a Docker Compose end-to-end
smoke test) wired into CI.

**Explicitly out of scope, not implemented, not claimed as implemented, not weakened:**
CV/AI quality analysis, MediaPipe Hands, any model training, P8, P9, Q2/Q3/Q4 — none of
these exist anywhere in this branch's diff. No new automatic competence/pass/fail decision
exists anywhere in this phase's code or UI strings. **Scoring, decisions, reassessment, and
Ed25519-signed reports already existed, complete, before this phase started (P2.2,
`docs/gates/P2_2.md`)** — this phase extends the review workspace's *presentation* of that
existing functionality (task tabs, a real evidence gallery/player, the audit log view) and
extends the audit log's scoring entries to record old/new values, but does not re-implement,
weaken, or re-claim any of it as P6 work. No worker password login or assessor mobile-app
role was added — the worker app still has no login (only a device-scoped self-registration
bootstrap, see below) and the assessor dashboard remains the only review surface.

## A real architectural gap found and a decision made explicit

Before any Android/server sync code was written, auditing the existing codebase surfaced a
genuine gap: P3–P5 are fully, deliberately offline (confirmed by `docs/gates/P5.md`'s own
"no HTTP call... anywhere in this codebase"), so the Android app has never once talked to the
server. But every existing server endpoint that creates an assessment
(`POST /assessments`) requires an **already-existing integer `worker_id`** referencing a real
`User` row — and no endpoint existed anywhere to create that row from a client call; only
`server/app/seed.py` ever created demo `User` rows, directly in the database, for local
testing.

This is a genuine product/security decision (a new, necessarily pre-authentication endpoint
that creates `User` rows), not an ordinary engineering choice, so it was put to the user
rather than decided unilaterally. The chosen design — confirmed by the user — is:
**`POST /workers/register`**, a public (no token, no password, no OTP) endpoint that accepts
the phone's own locally-generated, stable `device_worker_id` string (e.g. `"KP-A1B2C3D4"`,
the same `"KP-" + UUID` string `AppViewModel.register()` has generated since P3) and a display
name, and is idempotent: the same `device_worker_id` always resolves to the same `worker_id`,
created on first call. This matches the master plan's own stated design ("Worker ID is a
UUIDv7 made on the phone; the server confirms it at first sync") and the existing "no worker
login, ever" philosophy documented in `docs/worker_capability_tokens.md` — it is bootstrap,
not authentication; the worker capability token issued immediately afterward by
`POST /assessments` is what actually authorises every subsequent call.

A second, much smaller gap followed from the first: the phone only knows its pinned QP
code/version (`packs/ae-con-q0602/qp.json`, baked into the app), never the server's integer
`qualification_packs.id` — so a second, read-only, public lookup endpoint,
**`GET /packs/by-code`**, was added to resolve one to the other. This is a narrow,
uncontroversial addition (public pack metadata, no security tradeoff, no new write surface)
and was not re-raised as a separate decision point.

## Security properties, verified

1. **Product rule preserved.** The worker app has no login (confirmed: grep of this phase's
   diff for any password/OTP field on the worker side finds none); the assessor dashboard
   remains the only review surface (confirmed: no new worker-facing route in
   `apps/dashboard/src`).
2. **Capability-token design reused, not reinvented.** `POST /workers/register` and
   `GET /packs/by-code` are the only two new unauthenticated endpoints, and neither creates or
   exposes an assessment, evidence, or capability token — `POST /assessments` (unchanged)
   remains the sole issuer of the opaque worker capability token, returned exactly once, per
   `docs/worker_capability_tokens.md`'s existing design.
3. **HTTPS in release, cleartext confined to debug.**
   `apps/android/app/src/main/res/xml/network_security_config.xml` sets
   `cleartextTrafficPermitted="false"` with no debug overlay to weaken it in a release build;
   `apps/android/app/src/debug/res/xml/network_security_config.xml` is a debug-only resource
   overlay (AGP source-set precedence) that permits cleartext, solely so the physical manual
   gate below can reach a plain-HTTP local Docker Compose backend over the test Wi-Fi/hotspot.
   `app/build.gradle.kts`'s `verifyReleaseForbidsCleartextTraffic` task independently re-reads
   both files from source and asserts they genuinely differ — this is not a single global flag
   that could silently also apply to release.
4. **Bounded streaming, never a plaintext file.** `VaultStreamCipher.decryptingStream`
   (`core:seal`) is a true `InputStream` over Tink's own decrypting stream; `SyncRepository`
   reads it in fixed 1 MiB chunks and uploads each chunk's bytes directly — no
   `FileOutputStream` of plaintext exists anywhere in the sync code path.
   `SyncRepositoryInstrumentedTest.bounded_streaming_upload_never_writes_a_plaintext_copy_of_the_evidence_to_disk`
   seals a real photo, then exhaustively scans every file under the app's private storage for
   a known byte-marker from that photo's real plaintext, on a real device, after a real sync —
   zero matches.
5. **Every P5 integrity datum verified server-side.** `manifest_verify.py` verifies the
   ECDSA signature over the manifest's own canonical bytes (never a server-side
   re-serialization); `uploads.py`'s `_complete_evidence_upload` recomputes each item's SHA-256
   from the stored bytes (never trusts the client alone) and cross-checks it, the byte count,
   and the task binding against the already-verified manifest's declaration for that exact
   `evidenceId`.
6. **The server never marks a package reviewable until it is actually complete.**
   `submit_assessment`'s P6 gate requires `DeviceManifest.status == "complete"` — which itself
   only becomes true once every declared item has a matching, verified `EvidenceItem`
   (`_maybe_complete_manifest`) — before the assessment can leave `draft`.
   `test_submit_blocked_until_every_declared_item_is_verified` proves this with a manifest
   declaring two items and only one ever uploaded.
7. **Local data is never deleted early.** `SyncRepository.markSynced` deletes an item's
   encrypted vault file only after the server's receipt for that *exact* item is in hand (the
   `evidence_id`/`manifest_id` the server returned); the whole outbox + vault tree is deleted
   only after `POST /submit` itself succeeds.
   `a_server_rejected_evidence_upload_retains_local_encrypted_data_and_marks_failed_action_required`
   proves a rejected upload's vault file survives on disk and the assessment is never marked
   synced.
8. **No secret/plaintext/path in logs.** `SyncApiException.message` and
   `OutboxItemEntity.lastErrorCategory` are restricted to the fixed `SyncErrorCategory` enum
   (`NETWORK_UNAVAILABLE`, `INTEGRITY_REJECTED`, `SIGNATURE_REJECTED`, …) — never a raw
   exception message, server response body, file path, or the worker capability token.
   Grepped this phase's own new `Log.*`/exception-message call sites by hand to confirm.
9. **No baseline, no suppression, no fake path.** Every test added in this phase exercises
   real code (real ECDSA keys via the `cryptography` library server-side / Android Keystore on
   device, a real local HTTP socket via MockWebServer/a real FastAPI TestClient, real Tink
   encryption, real ffprobe/ffmpeg subprocess calls) — none of the new tests mock the security
   path they're meant to prove.

## Endpoint table (new/changed in this phase)

| Method | Path | Auth | Purpose |
|---|---|---|---|
| POST | `/workers/register` | none (idempotent on `device_worker_id`) | Establish a server-side worker identity on first sync |
| GET | `/packs/by-code` | none (public pack metadata) | Resolve the phone's pinned QP code/version to a server `pack_id` |
| POST | `/uploads` | `X-Worker-Token` | Begin/recover an upload session — now also accepts `target="manifest"`, `revision_id`, `client_evidence_id` |
| GET | `/uploads/{id}` | `X-Worker-Token` | Per-item received-chunk status, for resume |
| PUT | `/uploads/{id}/chunks/{n}` | `X-Worker-Token` | Upload one <=1 MiB chunk (unchanged wire shape; now also used for the manifest envelope) |
| POST | `/uploads/{id}/complete` | `X-Worker-Token` | Complete/verify — now also runs ECDSA signature verification (manifest) or manifest cross-check (evidence) |
| GET | `/assessments/{id}/sync-status` | assessor OR worker token | Per-item + manifest sync state, for resume-after-lost-ack and dashboard display |
| GET | `/assessments/{id}/audit-log` | assessor only | Full append-only accountability trail, including P6's sync-specific actions |
| POST | `/assessments/{id}/submit` | `X-Worker-Token` | unchanged route; now additionally gated on the current revision's manifest being `complete` when one exists |

`contracts/openapi.json` is regenerated and `python tools/export_openapi.py --check` passes
(see commands below) — every field/schema above is machine-readable there, not hand-described.

## Known limitations (genuinely outside P6 scope, not deferred P6 work)

- **The dashboard's "Declaration & QP match" card shows a summary snapshot only** —
  `matchResult`/`overallCoverage`/`gapTaskIdsCsv`, exactly what
  `AssessmentDraftEntity` durably persists on the phone. The worker's full declaration
  answers and the on-device "because" reasoning text are not persisted on the phone past the
  live session (an inherited P3/P4 scope boundary — see `docs/gates/P3.md`'s "Declaration...
  remain in-memory, ViewModel-scoped only") and so cannot be synced either. This is stated
  plainly in the card's own UI copy, not silently omitted.
- **CI does not run the real-device-only P6 instrumented tests**
  (`SyncRepositoryInstrumentedTest`, `AppDatabaseMigrationTest`) — the exact same
  GitHub-hosted-runner/no-AndroidKeyStore-in-any-emulator constraint P4/P5 already documented,
  unchanged by this phase. CI does compile the `androidTest` source set, so a build-breaking
  change there is still caught; the manual physical-device gate below is where this coverage
  is actually exercised, live.
- **No production release-signing config exists for the Android app** (unchanged from P4/P5)
  — `verifyP6TestOnlySyncOverrideDisabledInRelease` and `verifyReleaseForbidsCleartextTraffic`
  check the generated release `BuildConfig`/manifest/resources, which does not require a
  signing key.
- **A P5-era debug-only export directory is never cleaned up.**
  `EvidenceFileManager.debugExportDir`/`deleteDebugExportTree` (the `P5_TEST_ONLY` "Decrypt
  for verification" feature, gated out of release builds) has a working deletion function
  that nothing in the app's main source tree ever calls — confirmed by `grep` across
  `apps/android/app/src/main/kotlin`. This is a pre-existing P5 gap (the directory and its
  deletion helper both predate this phase), discovered incidentally during the P6 physical
  gate's whole-app plaintext sweep (see below), not introduced or worsened by P6, and out of
  this phase's scope to fix.

### Real bug found and fixed during this gate (not caught by the original automated suite)

1. **`SealOrchestrator.seal()` computed each evidence item's SHA-256 for the signed manifest
   but never persisted it back to the item's own database row.** `SyncRepository` requires
   `EvidenceDraftEntity.finalSha256` to upload an item and throws if it is null — so every
   real evidence item, on every real device, failed its first sync attempt with
   `UNKNOWN_SERVER_ERROR` ("evidence has no final hash"), confirmed via logcat's `KP-Sync`
   tag. No automated test caught this because none of them asserted on `finalSha256` at all —
   confirmed by grepping the full test suite for the field, zero matches, before the fix.
   Fixed by capturing a `sha256ByEvidenceId` map while building the manifest and writing it
   back via `evidenceDraftDao.update(item.copy(vaultRelativePath = ..., finalSha256 =
   sha256ByEvidenceId[item.id]))` in the same pass that encrypts each item into the vault.
   Covered by a new regression assertion in
   `full_real_seal_produces_a_real_keystore_signature_and_a_real_encrypted_vault_with_committed_outbox`
   (`SealOrchestratorInstrumentedTest`): `assertEquals(64, sealedRow.finalSha256?.length)`,
   with a comment explaining why this assertion exists — if `seal()` ever stops writing this
   field back, every real upload fails closed, exactly as it did here.
