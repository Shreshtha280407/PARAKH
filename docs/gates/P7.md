## 2. Computed outcome — pinned-data basis (no invented NSQF rule)

Pack data audited: `packs/ae-con-q0602/{qp,rubric,tasks}.json`.

- The **only** pinned numeric threshold anywhere in the pack is
  `qp.json.minimum_aggregate_passing_percent = 50`. There is no separate
  per-NOS percentage field, and `rubric.json`'s own `rules.pass_thresholds`
  text says explicitly: *"Read from the pinned QP file (never hard-coded)
  — see qp.json minimum_aggregate_passing_percent **and per-NOS marks**."*
  i.e. the rubric's own stated design is: compute each NOS's own percent
  from its pinned max marks, and compare it against the **same** pinned
  50% figure used overall — not a second invented number.
- `rubric.json.rules.critical_pc` (verbatim): *"level < 2 → that NOS
  cannot be marked competent, regardless of overall NOS %."* — matches the
  task brief's critical-PC rule exactly; `RubricItem.critical` already
  carries this flag per-PC from the pack, it is simply not consulted by
  any code yet.
- "Mandatory NOS" = the 5 task-evidenced NOS with a rubric scope
  (CON/N9001, N0602, N0604, N0603, N0605 — T1-T5). The other 3
  (CON/N8001, CON/N8002, DGT/VSQ/N0101) are explicitly
  `not_task_evidenced_nos` in `tasks.json`, declaration/notes-only, already
  out of rubric scope — not part of the computed-outcome rule.
- This interpretation reuses pinned data consistently at both scopes; it
  does not invent an official NSQF/CSDCI rule. Implemented in
  `server/app/outcome.py`, documented there with this same justification.

Outcome rule implemented (`server/app/outcome.py`), directly from §4.4 of
the master plan:

| Computed outcome | Rule |
|---|---|
| `RECOMMEND_CERTIFICATION` | every mandatory NOS meets its threshold AND no critical PC in any mandatory NOS is below level 2 |
| `PARTIALLY_COMPETENT` | some (not all, not none) mandatory NOS meet threshold-and-no-critical-violation |
| `NOT_YET_COMPETENT` | any critical PC below level 2, or most (>2 of 5) mandatory NOS below threshold |
| `INSUFFICIENT_EVIDENCE` | one or more mandatory-NOS PCs still `NOT_OBSERVABLE`/unscored — distinct from a demonstrated incorrect performance (level 0 with `DEMONSTRATED`) — signals a *reassessment candidate*, never silently counted as competent |

## 3. Task-specific reassessment + versioned resubmission — design

**Not** a new Assessment row. Extends the *same* assessment with a new
revision, reusing the exact P6 upload/manifest/revision_id machinery
already built (`DeviceManifest`, `EvidenceItem.revision_id`,
`UploadSession.revision_id`/`client_evidence_id`) rather than a parallel
protocol.

New tables (migration, §6/§7 of this doc once written):
- `assessment_revisions` (assessment_id, revision_number, revision_id
  [nullable until a manifest lands], reopened_task_codes JSON [null =
  revision 1 = everything], status, created_at, submitted_at)
- `reassessment_requests` (assessment_id, task_codes JSON, reason NOT
  NULL, capture_instructions NOT NULL, requested_by_id, requested_at,
  status, fulfilled_by_revision_id)

**Critical P6 integration constraint, confirmed by the Android audit**:
`SyncRepository.finishIfAllSynced()` deletes the **entire** vault
directory (`fileManager.deleteVaultTree(assessmentId)`) and **all**
outbox rows once a revision fully syncs — so v2 cannot re-encrypt/re-send
v1's unchanged-task bytes, they are gone from the device. However
`EvidenceDraftEntity`'s metadata columns (`finalSha256`, `finalBytes`,
`finalMimeType`, dimensions) are **not** cleared, only the vault **file**
is deleted (`EvidenceFileManager.deleteQuietly`) — confirmed by reading
`SyncRepository.markSynced`/`DraftModels.kt`. So the phone can still
truthfully re-declare an unchanged item's exact `(evidenceId, sha256,
bytes, task)` in a new signed manifest without touching the file.

Server-side, this requires **no new manifest JSON field**. The existing
`_maybe_complete_manifest` already matches declared items against
`EvidenceItem` by `(assessment_task_id, client_evidence_id)` with no
revision check at all — so an unchanged item re-declared with the same
IDs in a v2 manifest is already recognised as "satisfied" by the v1 row,
with zero new matching code. Two real gaps are being closed, not invented:
1. **No cross-check today** that a re-declared "inherited" item's
   `sha256`/`bytes` actually match the existing row — a buggy/malicious
   v2 manifest could silently declare a different hash and have it
   accepted. New: reject the manifest if a declared item matches an
   existing `(task, client_evidence_id)` whose stored
   `sha256`/`declared_size_bytes` differ from the new declaration.
2. **No check that a non-reopened task's evidence set didn't change** — a
   v2 manifest declaring a *new* `client_evidence_id` for a task outside
   `reopened_task_codes` must be rejected outright (locked-task
   enforcement is server-side, not just a UI affordance).
3. `open_upload_session`'s `assessment.status != "draft"` gate is relaxed
   to also allow `needs_reassessment`, but only for a brand-new
   `revision_id` and (for `target="evidence"`) only when `task_code` is in
   the active `assessment_revisions` row's `reopened_task_codes`.
4. Budget enforcement for v2 uses the **manifest's own declared
   totals** (`declared_total_bytes`/`task_totals`, already captured at
   manifest-receive time) checked against pack/task budgets at manifest
   acceptance — this is the *active revision's full snapshot* (inherited +
   new), so it naturally satisfies "historical storage doesn't
   double-count" (inherited bytes were never re-uploaded, so
   `task.bytes_used`/`total_bytes_used` only grow by genuinely new bytes)
   while still bounding the full v2 picture via the manifest total.
5. Resubmit path: once the active revision's manifest reaches `complete`
   (every declared item — inherited and new — verified), a new
   `POST /assessments/{id}/submit` call (same worker token) is accepted
   from `needs_reassessment` status, moves to `submitted`, marks the
   `assessment_revisions`/`reassessment_requests` rows fulfilled.
6. v1 stays immutable: no code path ever mutates an existing `EvidenceItem`
   or `AssessmentCriterionScore` row in place for this flow — v2 only adds
   new rows (new evidence for reopened tasks, re-reviewed scores bumping
   `version`) and the dashboard renders both by `revision_number`.

`GET /assessments/{id}/worker-updates` (new, dual-auth like
`/sync-status`): returns the latest pending reassessment request (if any),
current assessment status, and report pending/available — a snapshot read,
not a generic event log (simpler, and inherently idempotent/replay-safe
since every poll just reads current DB state). This is a deliberate,
documented departure from the master plan's literal
`GET /workers/me/updates?since=` shape: that shape presumes a worker
**session/login** concept ("me") the product explicitly does not have
(see `docs/worker_capability_tokens.md`) — the functional requirement
(durable, idempotent, cursor-aware delivery of reassessment
requests/status/report-availability to the worker app) is preserved,
scoped instead to the existing per-assessment capability-token model.

## 4. Report signing redesign — PDF-first, detached, key-history-aware

Current `report_signing.py` signs a JSON snapshot; the PDF is a
re-rendering of that snapshot plus the already-known signature text, and
is **re-generated on every download** — there is no stored immutable PDF
or PDF-bytes hash. This does not meet P7's explicit requirements (render
PDF bytes → hash → sign, store immutable artifact, never resign on retry,
offline-verifiable with a one-byte-tamper-fails guarantee against a real
stored file). Redesign:

1. `generate_report`/new `sign-off` endpoint renders the PDF deterministically
   from a DB snapshot (**not** including any hash/signature field — avoids
   the circularity the task flags), computes `sha256(pdf_bytes)`, signs
   that digest with Ed25519 (same `cryptography` primitive already used),
   stores the **immutable** PDF bytes via the existing `Storage` interface
   (`reports/{report_uid}.pdf`), and persists `pdf_sha256`, `signature`,
   `key_id`, a new stable `report_uid` (public, not the raw assessment id),
   and `revision_number`.
2. `GET /assessments/{id}/report?format=pdf` now serves the **stored**
   bytes (no re-render); `format=json` still serves an informational
   (unsigned) snapshot for audit/debugging.
3. `GET /verify/{report_id}` (new, public, `report_id` = `report_uid`):
   `{status, qp_code, qp_version, recommendation, sha256}` — matches the
   plan's exit-test output shape, still never leaks worker PII/evidence.
4. Key history: `settings.report_signing_key_id`/`_private_key` remain the
   *current* signing key; a new optional `REPORT_SIGNING_KEY_HISTORY` env
   var (comma-separated `key_id:hex_public_key` pairs) lets `verify()`
   resolve an **older** `key_id` to its retired public key, so a report
   signed by a previous key stays verifiable after rotation.
5. `config.py`'s dev-mode ephemeral-key-per-restart auto-generation is
   **removed** — `REPORT_SIGNING_PRIVATE_KEY` is now required in every
   environment including development (already set in this repo's local
   `.env` and in CI's smoke-test `.env`, so neither breaks); absence fails
   fast with an explicit message, satisfying "never generate a fresh key
   on every restart" without touching any already-working config.
6. `tools/verify_report.py`: offline CLI. Takes the PDF file + a detached
   JSON receipt (`{pdf_sha256, signature, key_id}` — downloaded alongside
   the PDF via a small receipt-fetch helper/endpoint) + a trusted public
   key (hex or PEM, `--pubkey`), independently re-hashes the PDF bytes and
   verifies the Ed25519 signature. A one-byte-modified copy of the PDF
   fails (different hash). This uses a **detached** signature/receipt as
   the task text explicitly permits ("use a detached signature/receipt
   where necessary; avoid a circular requirement to embed the PDF's own
   final hash/signature inside itself") — the master-plan illustrative
   command (`verify_report.py out/report_X.pdf --pubkey ...`) is treated
   as illustrative per the task's own instruction that illustrative output
   counts are not a literal contract; the receipt file travels alongside
   the PDF by convention so the real workflow matches the plan's spirit.

## 5. Password-confirmed sign-off

New `POST /assessments/{id}/sign-off`: `{password, final_recommendation,
override_reason?}`. Assessor/admin only; re-verifies `password` against
the **authenticated** user's stored hash via the existing
`auth.verify_password` (already used for login, nothing new to write for
the crypto itself) — never trusts a frontend-only confirmation. Wrong
password → 401. Blocked (409) while any `reassessment_requests` row for
this assessment is still `pending`. Computes the outcome (§2); if
`final_recommendation` differs from the computed one, `override_reason`
must be non-whitespace or the request is rejected 422. Writes `AuditLog`
with assessor id, timestamp, original computed value, final value, score
pack/rubric version, and the reason. Never logs/stores the password itself.

  sign-off (including a deliberate wrong-password rejection), the
  revision-history panel, and the public `#/verify/:reportId` page — all
  against real API responses, not stubbed data. One suspected bug
  (apparent stale cross-assessment panel state) was investigated and

**Incident, disclosed in full**: while re-running the Docker smoke
scripts a second time (to get a fresh, real, citable pass rather than
relying on memory of the earlier run), the root `.env` was overwritten
via a Bash heredoc **without reading or backing it up first** — a
genuine process mistake, not an intended action. `.env` is gitignored
with no git history, so it was not recoverable from version control.
Recovery (performed with the user's explicit, step-by-step authorization
after disclosure, never unilaterally):

- Confirmed no running process still held the old values in memory.
- Found no other on-disk checkout or editor backup with a usable `.env`.
- The `kaushalpramaan-mvp_dbdata` Docker volume had survived (an earlier
  `docker compose down` without `-v` removes containers, not volumes).
  Copied it **read-only** into a separate, newly-created volume and
  inspected only that copy — never the original.
- Recovered, by name, with high confidence from real rows in that
  volume's `signed_reports`/`users` tables: `REPORT_SIGNING_KEY_ID`
  (`dev-key-1`) and `DEV_ASSESSOR_EMAIL`, both confirmed unchanged from
  `.env.example`'s documented defaults. All assessments/reports found in
  that volume were confirmed to be this session's own seed/smoke-test/
  Playwright-testing data, not pre-existing data from before this work
  began.
- `JWT_SECRET`, `DEV_ASSESSOR_PASSWORD`, and `REPORT_SIGNING_PRIVATE_KEY`
  were confirmed genuinely unrecoverable by design — a one-way argon2
  hash and values never persisted outside the process environment,
  respectively — not merely "not found."
- Fresh values were generated for those three, under a **new**
  `REPORT_SIGNING_KEY_ID` (never reusing `dev-key-1`, since that specific
  private key is gone — the two reports signed under it before this
  incident are local test artifacts only, left exactly as they are, not
  re-signed or claimed to pass). The demo assessor's password hash was
  updated with a single scoped `UPDATE ... WHERE email = ...` against
  the real volume, row counts confirmed unchanged before/after.
- Re-verified end to end against the real stack: login, a fresh
  password-confirmed sign-off, public verify, a tampered-copy offline
  verify failure, and all of the above still working after an actual
  container restart (secrets are not regenerated on restart). Both
  smoke scripts (37 steps) re-run clean under the new secrets.
- The temporary recovery-copy volume was deleted after inspection, with
  the user's confirmation. The real `dbdata`/`evidence` volumes were
  never deleted or modified beyond the one scoped password-hash row.

Lesson applied immediately and going forward: any further local
Docker-based verification uses a throwaway `.env`/project name/volumes
distinct from the real one, and the real root `.env` is never written to
via Bash without reading it first.
