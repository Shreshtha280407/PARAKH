# P-3 gate — offline Android worker-flow app with mock evidence

Phase owner: this completion pass. Window: 2026-10-10. Branch:
`feature/q1-p3-complete`.

## Scope

Complete offline Android worker-flow app, Kotlin/Jetpack Compose, reading
the Q-1 matcher (`docs/gates/Q1.md`) on-device:

1. Language selection (English/Hindi, changeable at any time)
2. Consent (clear text, optional on-device TTS, cannot continue without it)
3. Registration (phone, 4-digit PIN, generated worker UUID; in-memory state
   only — no Room, that is P-4)
4. Structured self-declaration feeding the Kotlin matcher directly
5. Offline QP match result: Assistant Electrician CON/Q0602 only, outcome +
   "because" lines + gap NOS, never certified/qualified/passed/failed, never
   another QP
6. Task flow: real T1-T5 pack from `packs/ae-con-q0602/tasks.json`, guides,
   evidence hints, per-task + 120 MB total budget, gap tasks marked "extra
   evidence needed", safety warning (de-energised board only)
7. Mock evidence workflow: add/replace/remove, configurable fake byte
   sizes, date/time, per-task and total budget enforcement, clear errors
8. Preview, attestation ("This evidence shows my own work."), local submit
   to "Sealed locally — waiting for sync", explicit no-upload messaging
9. Navigation, accessibility, resilience (rotation-safe via ViewModel, large
   tap targets, content descriptions, no network permission/calls)

**Explicitly out of scope, not claimed as completed:** real CameraX
capture, Room persistence, encryption, video compression, WorkManager sync,
server upload, CV models, report generation, dashboard changes. Outside the
approved Q-1/P-3 scope.

## Real bugs found and fixed while getting this green

Three genuine issues surfaced building and testing this, not scripting
typos — recorded here because the task that commissioned this work asked
for honesty about what actually happened, not a clean narrative:

1. **Gradle/Kotlin incremental-compilation corruption from two concurrent
   daemons.** Early in this session a standalone `gradle` binary (used to
   bootstrap the wrapper) and the project's own `./gradlew` were both
   invoked against the same project, each spinning up its own Gradle+Kotlin
   daemon pair against the *same* incremental-compilation caches. This
   produced two different failure modes on different runs:
   `NoClassDefFoundError: MainActivity` (a dex genuinely missing the launcher
   activity class despite a "successful" build) and
   `CONFLICTING_OVERLOADS` (the compiler reporting a function defined twice
   when it was defined once). Both vanished permanently after
   `./gradlew --stop`, killing every stray `GradleDaemon`/
   `KotlinCompileDaemon` process, and doing one `./gradlew clean` + fresh
   build using **only** the project's own `./gradlew` from then on. Fix is
   procedural (one build tool, one daemon lineage), not a code change.
2. **`performScrollTo()` cannot reach a not-yet-composed `LazyColumn`
   item.** `DeclarationScreen`'s ~50-item list is lazy; scrolling to a
   specific answer chip by tag only works once that chip has already been
   composed, which it isn't if it is far from the current scroll position —
   a chicken-and-egg failure (`onNodeWithTag(tag).performScrollTo()` needs
   to find the node to scroll to it, but the node does not exist yet).
   Fixed by tagging the `LazyColumn` itself and using
   `performScrollToNode()` on the *container*, which drives the lazy list's
   own index-aware scroll action while searching for the target — the
   correct, documented pattern for testing off-screen lazy content. See
   `apps/android/app/src/androidTest/kotlin/in/kaushalpramaan/app/TestFlows.kt`.
3. **Ambiguous text assertions against a screen title shown twice.**
   `ConsentScreen` and `SubmittedScreen` rendered the same string both in
   the top app bar and as a body headline; `onNodeWithText(...).assertIsDisplayed()`
   requires exactly one match and failed with "found 2 nodes." Fixed by
   removing the redundant body headline on `ConsentScreen` (the top bar
   already shows it) and asserting via the body's `testTag` instead of text
   on `SubmittedScreen` (its body copy carries the celebratory checkmark
   icon and is worth keeping distinct from the bar).

None of these were business-logic bugs in the matcher or the declaration/
evidence/budget code — all three were test-infrastructure and build-tooling
issues, found by actually running the suite rather than assuming it would
pass.

A fourth, genuinely code-level finding came from `./gradlew lint`:
**`LocalContextConfigurationRead`** (error severity) in `MainActivity.kt`'s
`LocalizedApp` — the in-app language-switch helper built its override
`Configuration` from `context.resources.configuration` directly, which
Compose's lint rules flag because that read is not itself
recomposition-tracked (a future refactor relying on implicit Configuration
invalidation could silently see a stale value). Fixed by sourcing the base
Configuration from `LocalConfiguration.current` instead — the
Compose-tracked value — while still keying the `remember` block on
`language` explicitly, which is what actually drives the locale switch here.
`./gradlew lint` is clean after the fix (`BUILD SUCCESSFUL`, HTML/SARIF
reports under `apps/android/app/build/reports/`); the full suite (unit +
instrumented) was re-run afterward and still passes, confirmed below.

## What each instrumented test actually proves

- **AppropriateMatchFlowTest** — full journey, English, every declaration
  item answered "often" (the same scenario as `golden_vectors.jsonl` G001:
  `overall_coverage=0.9113`, `appropriate_match`, zero gaps). Walks
  language → consent → registration → declaration → match result (asserts
  "Appropriate match", the "because" reasons section, and "no gap areas") →
  task list → add one mock evidence item → preview → attestation → submit
  → sealed state, then asserts the app holds no `INTERNET` permission.
- **PartialMatchFlowTest** — every item answered "sometimes" (G002:
  `overall_coverage=0.5468`, `partial_match`, all 5 NOS in `gap_nos`).
  Asserts the gap section is populated and that all 5 tasks (T1-T5) carry
  the "Extra evidence needed" badge on the task list.
- **HindiFlowTest** — the P-3 exit test verbatim ("a non-team person
  completes the flow in Hindi without help"): language screen → Hindi
  selected → every subsequent screen's text asserted in Hindi → full
  journey to sealed state.
- **EvidenceBudgetTest** — fills T1's 15 MB budget exactly in one mock
  item, asserts a second add is rejected with the specific error message
  and a disabled Save button, removes the item and asserts the task shows
  "no evidence" again (budget recalculated to 0), then adds and replaces an
  item and asserts exactly one item remains (no duplicate).
- **OfflineAirplaneModeTest** — toggles the emulator into airplane mode via
  `cmd connectivity airplane-mode enable` before the test and back off
  after, and completes an appropriate-match journey through the task list
  while it is on, alongside the same no-`INTERNET`-permission assertion.

## Limits, stated honestly

- State is ViewModel-scoped in-memory only; survives rotation, not process
  death or app restart. Room persistence is P-4, not claimed here.
- Mock evidence items carry a configurable fake byte size and metadata only
  — no real photo/video bytes, no camera permission requested anywhere.
- TTS on the consent screen is a best-effort affordance (degrades
  gracefully with no voice pack installed); the flow never blocks on it.
- Detailed task step-by-step guides (`tasks.json`'s `step_guide`) are shown
  in English only, sourced verbatim from the canonical bundled pack —
  translating pack content itself (as opposed to UI chrome) was judged out
  of scope to avoid a second, hand-maintained bilingual copy of canonical
  task-pack data; task titles, navigation, safety warnings, declaration
  cards, match results and all other UI chrome are fully bilingual.
- CI (`.github/workflows/ci.yml`) builds the Android app and runs all JVM
  `core:mapping` tests, but does not run the emulator instrumented suite —
  GitHub-hosted runners lack reliable nested virtualization for the Android
  emulator. This is a platform constraint, documented in the CI file itself,
  not an incomplete P-3 feature: the instrumented tests exist and the
  commands above reproduce them exactly, on a real emulator, as run in this
  session.
