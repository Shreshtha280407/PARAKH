## C. Real resumable evidence upload

### C1/C2 — Protocol

- **Chosen protocol**: ordered sequential chunks, documented in
  `server/app/routers/uploads.py`'s module docstring (also summarised in
  `docs/gates/P2_1.md` here): `chunk_index` must equal the session's
  `next_chunk_index`, or be exactly the previous one (idempotent replay).
  `GET /uploads/{id}` reports `received_bytes` / `next_chunk_index` for
  resume.
- **Quota reservation**: `claimed_size_bytes` is reserved the instant the
  session opens (`quota.task_bytes_committed` counts open, non-expired
  sessions **and** completed evidence together) — see C3 for the test
  proving this across two sequential calls (P2.1) and `docs/gates/P2_2.md`
  section 0A for the real concurrent proof, added in P2.2, that the
  reservation also holds when two requests race each other.
- **Server-side hash**: `storage.sha256()` streams the stored file through
  SHA-256 in 1 MB chunks; `client_sha256` is compared against it, never
  trusted alone.
- **Atomic finalisation**: `EvidenceItem` is created in the same DB
  transaction as the session's `status="completed"` update — verified live
  (C below) and in tests.
- **Idempotent complete**: retrying `/complete` after success returns the
  identical receipt (same `evidence_id`), confirmed no duplicate row is
  created.
- **Private storage**: `server/app/storage.py`'s `LocalDiskStorage`, keys
  are server-generated (`upload_key_for`, never a client filename), path
  traversal is rejected (`test_path_traversal_is_rejected`). Mounted as a
  **named Docker volume** (`evidence:/data/evidence`), never under a path
  nginx (the dashboard's web server) serves — confirmed live: `curl` to the
  evidence path via the dashboard's public port returns 404 (see G).
- **Expiry**: `UploadSession.expires_at` (default 2h,
  `UPLOAD_SESSION_TTL_MINUTES`); expired-but-still-"open" sessions are
  excluded from quota reservation lazily (`quota.py`'s query filters
  `expires_at > now()`), and a `PUT` against an expired session flips it to
  `"expired"` and returns 409.

### C3 — Tests

- **Command**: `python -m pytest server/tests/test_uploads.py -v`
- **Expected**: 21/21 pass, covering —
  normal upload + completion; interrupted upload + resume (status after a
  partial chunk, then finish); replaying the last acked chunk (idempotent,
  byte count doesn't double); out-of-order chunk (409); chunk exceeding the
  declared total (409); incorrect total size at complete (409, "size
  mismatch"); incorrect hash at complete even with correct size (409,
  "hash mismatch", session stays open for retry); duplicate complete call
  (same receipt, not a new `EvidenceItem` — DB-counted); quota exceeded at
  open (409); **two *sequential* open-session calls** on the same task
  jointly exceeding its budget (409) — note this proves the reservation
  model is correct across two separate requests one after another, **not**
  that it holds under real concurrency (two requests racing each other).
  Nothing in P2.1 closes that race: `check_quota` reads committed state and
  the caller then inserts the `UploadSession` as two separate steps with no
  row lock between them, so two simultaneous callers can each observe
  "fits" before either commits. P2.2 adds the actual fix (`SELECT ...
  FOR UPDATE` on the assessment row in `open_upload_session`) plus a real
  two-thread/two-connection Postgres test that fails without that lock —
  see `docs/gates/P2_2.md` section 0A and
  `test_concurrent_reservations_on_same_task_never_jointly_exceed_its_budget`
  in `server/tests/test_uploads.py`; evidence receipt appears correctly on
  assessment detail.
- **Live verification** (not just pytest): a real curl-driven
  open → chunk → complete cycle against the **Dockerized** stack, with a
  real 1 MB random file — server-computed SHA-256 matched the file's real
  hash exactly; a second, deliberately-oversized session open got 409; a
  deliberately-wrong-hash complete got 409; the stored file was found on
  the private volume via `docker compose exec api find /data/evidence` and
  was **not** reachable via the dashboard's public port (404). Full
  transcript in this phase's build log.

## D. Durable background jobs / worker

### D1/D2 — Jobs table, claim logic, worker

- **Command**: `python -m pytest server/tests/test_jobs.py server/tests/test_worker.py -v`
  (requires `TEST_DATABASE_URL` pointed at real Postgres for one test — see below)
- **Expected**: `test_jobs.py` 8/8, `test_worker.py` 6/6.
- **Columns**: `id, type, payload, status, attempts, max_attempts,
  locked_at, locked_by, last_error, created_at, started_at, finished_at` —
  exactly as specified (`server/app/models.py::Job`).
- **Queue backend**: PostgreSQL only, `SELECT ... FOR UPDATE SKIP LOCKED`
  (`server/app/jobs.py::claim_job`) — no Redis/Celery.
- **Enqueue**: after a successful `/uploads/{id}/complete`, a
  `verify_evidence` job is enqueued (`routers/uploads.py`).
- **Worker**: `python -m app.worker` (Docker) / `python -m server.app.worker`
  (local) — polls, claims one job, dispatches by `type`, retries up to
  `max_attempts` then marks `failed`; structured logs
  (`parakh.worker`/`parakh.jobs` loggers, one line per claim/success/retry/failure).
- **The job itself**: `verify_evidence` re-streams the stored file through
  SHA-256 and compares it to the `EvidenceItem.sha256` recorded at upload
  time — real, meaningful work (catches silent volume/disk corruption
  between upload and later use), deliberately **not** thumbnailing or any
  CV/AI inference (out of scope, see master plan's own "verify, thumbnail,
  report later" framing).

### D3 — Concurrency proof, not just unit tests

- **Command**: `TEST_DATABASE_URL=postgresql+psycopg://parakh:parakh_test_pw@localhost:5432/parakh_test python -m pytest server/tests/test_jobs.py::test_concurrent_claims_never_double_process -v`
- **Expected**: PASS. Two real threads, two independent DB connections,
  20 queued jobs, drained concurrently — asserts all 20 were claimed
  exactly once each (`len(set(all_claimed)) == 20`), both workers claimed
  at least one (proves real concurrency happened, not accidental
  serialisation), and zero jobs remain queued.
- **Honest limitation, by design**: this test refuses to run (hard
  `pytest.fail`, not a skip) against SQLite, because SQLite has no
  row-level locking and the guarantee literally cannot be demonstrated
  against it. CI's `p2-backend-tests` job runs the **entire** suite against
  a real `postgres:16-alpine` service container for exactly this reason —
  see `.github/workflows/ci.yml`.

## Known, stated limitations (carried forward openly)

1. No report/signed-PDF, no scoring/reassessment endpoints — explicitly
   out of scope for this branch (master plan P6/P7), nothing here fakes
   them.
2. No CV/AI inference, no thumbnailing — the worker's one job type
   (`verify_evidence`) is a hash re-check, nothing more.
3. Worker capability tokens have no rotation/revocation/recovery flow —
   documented boundary in `docs/worker_capability_tokens.md`, not hidden.
4. `sessionStorage` for the dashboard's JWT is demo-grade, not
   pilot-grade (still vulnerable to XSS exfiltration) — stated in
   `src/auth.ts` and this doc, not glossed over.
5. CORS is `allow_origins: ["*"]` by default (`CORS_ALLOW_ORIGINS` env
   var) — fine for a same-machine demo stack with Bearer-only auth (no
   cookies), called out in `server/app/config.py` as something to tighten
   before any non-demo exposure.
6. The Docker stack's own build needs internet for image/package pulls —
   see G above for exactly what "offline" does and doesn't mean here.
7. `CON/N0603.PC16` (diesel generator maintenance) remains
   `NOT_APPLICABLE_IN_MVP` from P1.1 — untouched by this branch, carried
   forward as-is.
