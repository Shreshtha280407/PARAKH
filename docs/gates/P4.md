# P-4 gate — offline evidence capture, durable drafts, preview/retake/replace/delete

Phase owner: this completion pass. Window: 2026-10-11. Branch: `feature/p4-offline-capture`,
based on `feature/q1-p3-complete` (origin/main was stale relative to that branch at the time
this work started — it was missing P3/Q1 entirely — so this branch is based on
`feature/q1-p3-complete` instead, with the user's explicit confirmation; see git log for the
exact ancestry).

## Scope

In scope, implemented and verified below:

1. Real CameraX photo and video capture (back camera, no mock evidence) into app-private
   internal storage — never MediaStore/Gallery/Downloads/DCIM, never a cache-only directory.
2. A local, Room-backed, **SQLCipher-encrypted** draft database (`AssessmentDraft` /
   `TaskDraft` / `EvidenceDraft`), with the passphrase itself generated once and stored only
   in its Android-Keystore-encrypted form (never as plaintext, never logged).
3. Crash-safe evidence lifecycle: staging → promote (atomic rename) → READY, with
   launch-time reconciliation that recovers every interrupted state (mid-capture, mid-delete,
   mid-replace, or a true orphan file) without ever silently losing or duplicating evidence.
4. Local preview (downsampled photo bitmap, streamed video playback), retake, replace
   (old item preserved until the new one is fully READY, then removed), and delete
   (destructive-action confirmation required).
5. The five fixed per-task safety ceilings and the 120 MB assessment-total ceiling, read from
   the canonical `packs/ae-con-q0602/tasks.json` pack (never a second, hand-duplicated copy),
   enforced live during recording via CameraX's own byte-count stream.
6. A 300 MB free-space preflight before any capture starts.
7. SD (480p) default / HD (720p) opt-in video quality, with automatic fallback if the device
   doesn't support the requested profile.
8. A debug-build-only, visibly-labelled `P4_TEST_ONLY` 4 MB test ceiling override, wired
   through the exact same production ceiling-enforcement code path, and proven baked out of
   release builds as a compile-time constant (not a runtime flag).
9. The whole worker flow and the fixed five Assistant Electrician tasks from P3, unchanged;
   the QP/rubric/mapping content, unchanged (`tools/audit_qp_traceability.py` still passes
   all 10 checks).

**Explicitly out of scope, not claimed as completed:** P5 (final evidence
compression/fitting, final encryption, SHA-256 receipts, sealing, encrypted outbox creation)
and P6 (resumable upload/sync, assessor dashboard consumption). This is a scope statement,
not a deferred P4 requirement — P4's own evidence model (private app-local draft media,
SQLCipher-encrypted metadata) is complete and correct on its own terms; P5/P6 will later
*consume* it, not finish it.

## Architecture

### Local encrypted database

- `apps/android/app/src/main/kotlin/in/kaushalpramaan/app/data/draft/AppDatabase.kt` — Room
  database, version 1, `exportSchema = true` (the real exported schema is committed at
  `apps/android/app/schemas/in.kaushalpramaan.app.data.draft.AppDatabase/1.json`). Opened via
  `net.sqlcipher.database.SupportFactory(passphrase)` as the Room `openHelperFactory` — the
  real `net.zetetic:android-database-sqlcipher` native library, not a mock.
- `DatabaseKeyProvider` generates a 32-byte random passphrase once (`SecureRandom`, not a
  human-memorable "password") and stores it only inside `androidx.security.crypto`'s
  `EncryptedSharedPreferences`, itself backed by a `MasterKey` (AES-256-GCM) generated inside
  — and never exported from — the Android Keystore. The raw passphrase is never written to
  disk, logged, or placed in `SharedPreferences` as plaintext.
- `DraftModels.kt` — `AssessmentDraftEntity` / `TaskDraftEntity` / `EvidenceDraftEntity` plus
  their lifecycle-state enums (`AssessmentDraftState`, `TaskDraftState`, `EvidenceDraftState`).
  `isTestOnly` is `true` on every draft created through this phase — P4 is a technical capture
  test, never a real RPL assessment, and the task list visibly labels it `P4_TEST_ONLY`.
- `DraftDaos.kt` — Room DAOs, `Flow`-returning reads (DB changes push straight into the UI via
  `AppViewModel`'s `StateFlow`), suspend writes.

### Private draft storage

- `EvidenceFileManager.kt` — all evidence lives under
  `context.filesDir/drafts/<assessmentId>/<taskId>/<evidenceId>[.staging].<ext>`, app-private
  internal storage only. No `MediaStore` call, no external-storage permission, no Gallery
  picker anywhere in the app (`app/build.gradle.kts`'s `verifyNoGalleryImportPath` task scans
  every `.kt` file under `src/main` for `ACTION_PICK`/`ACTION_GET_CONTENT`/
  `ACTION_OPEN_DOCUMENT`/`ACTION_OPEN_DOCUMENT_TREE` and fails the build if any appear).
- Capture writes to a `.staging.<ext>` file first. Promotion is a same-directory
  `File.renameTo` — atomic on a single filesystem volume — only after CameraX reports success
  and the file's metadata (bounds for photos via `BitmapFactory.Options.inJustDecodeBounds`,
  duration/dimensions for video via `MediaMetadataRetriever`, neither of which decodes pixel
  or frame data) has been read.

### Evidence lifecycle and crash recovery

`EvidenceRepository.kt` is the single orchestration point; no other code touches the DAOs or
file manager directly.

- **Replace**: the new item is captured fully independent of the old one
  (`replacesEvidenceId` recorded on the new STAGING row from the start). Only once the new
  item reaches READY is the old item removed via the same delete routine. If the process dies
  in between, `reconcileOnLaunch()` finds the READY row's still-set `replacesEvidenceId`,
  finishes deleting the old item, and clears the pointer — forward recovery, not a dangling
  duplicate.
- **Delete**: mark `DELETED` (committed) → delete the file → hard-delete the row. A crash
  between any of these steps leaves a `DELETED` row that `reconcileOnLaunch()` finds and
  finishes on the next launch.
- **Interrupted capture**: if a `STAGING` row's *final* file already exists on disk (the
  rename succeeded but the DB commit didn't), reconciliation finishes the promotion in place.
  If neither the final nor a usable staging file exists (the process died mid-write),
  reconciliation deletes any partial bytes and marks the row `FAILED` — visible to the user,
  removable through the normal delete action, never silently resurrected as a lie.
- **Orphan sweep**: any file on disk with no matching DB row at all (impossible via the
  app's own code paths, but defensive against a crash before the very first DB insert) is
  deleted; files belonging to *other* valid tasks/evidence are never touched.
- **Whole-draft delete**: same mark-then-remove pattern at the assessment level (`TaskListScreen`'s
  "Delete this test draft" action, with a destructive-confirmation dialog) — removes every
  task/evidence row and the entire `drafts/<assessmentId>/` directory tree.

All of the above lifecycle rules are exercised directly (not re-implemented as test doubles)
by `EvidenceRepositoryTest` — see "Automated commands and results" below.

### Resume-on-launch

`AppViewModel.init` runs `reconcileOnLaunch()` once per process start, then looks for the one
active (non-deleted) `AssessmentDraft`. If one exists, the app resumes straight to the task
list (skipping language/consent/registration/declaration, which stay in-memory-only and are
not P4's concern) with the task list's gap badges reconstructed from a small cached snapshot
of the match result taken when the draft was created. If none exists, the app starts at the
language screen exactly as before. A brief `LoadingScreen` covers the one-time async check.

### Task safety budgets, free-space preflight, SD/HD, debug test ceiling

| Task | Budget |
|---|---|
| T1 — Safety & PPE | 15 MB (15,728,640 bytes) |
| T2 — Tools & meter use | 20 MB (20,971,520 bytes) |
| T3 — LV wiring (switchboard) | 30 MB (31,457,280 bytes) |
| T4 — Temporary lighting / fault | 25 MB (26,214,400 bytes) |
| T5 — Temporary LV panel | 30 MB (31,457,280 bytes) |
| **Assessment total** | **120 MB (125,829,120 bytes)** |

These are read live from `packs/ae-con-q0602/tasks.json` via `core:mapping`'s existing
`Rules`/`TasksFile` — the same canonical source the P3 task list and the Python matcher
already use. P4 never hand-duplicates these numbers; `EvidenceRepositoryTest`'s
`fixed_task_budgets_and_total_match_the_agreed_configuration` test pins the exact byte values
above against the real loaded pack, so pack drift would fail a test, not silently change
behaviour.

`EvidenceRepository.beginCapture()` computes one `effective ceiling = min(remaining task
budget, remaining total budget[, debug test ceiling])` before a capture is allowed to start,
and the CameraX capture controller (`CaptureSession.kt`) stops recording the instant measured
bytes reach that number — one enforcement path, not two independently-computed limits.

Free-space preflight: `EvidenceFileManager.MIN_FREE_BYTES_REQUIRED = 300 MB`, checked via
`StatFs` on the internal-storage volume immediately before any capture starts; below that,
capture is refused with a clear, recoverable message (`capture_error_insufficient_space`).

Video quality: `VideoQualityChoice.SD` (Quality.SD / 480p) is the default; `HD` (720p) is an
explicit in-app toggle. Both go through `QualitySelector.from(quality,
FallbackStrategy.lowerQualityOrHigherThan(quality))`, so an unsupported profile falls back to
the next available one automatically rather than failing.

Debug-only test ceiling (`P4_TEST_ONLY`): `app/build.gradle.kts`'s `debug` build type sets
`buildConfigField("boolean", "P4_TEST_ONLY_CEILING_ENABLED", "true")` and
`buildConfigField("long", "P4_TEST_ONLY_CEILING_BYTES", "4_194_304L")`; the `release` build
type hardcodes both to `false`/`0L`. These are **compile-time constants per build variant**,
not a runtime setting — there is no code path that can flip them on in a release build. The
capture screen only renders the override toggle at all when
`BuildConfig.P4_TEST_ONLY_CEILING_ENABLED` is true, and it is visibly labelled
`P4_TEST_ONLY ceiling: 4.0 MB (debug builds only)`. A dedicated Gradle task,
`verifyP4TestCeilingDisabledInRelease`, generates the real `release` variant's `BuildConfig`
and parses it to assert both fields are `false`/`0` — see its real output below.

### Structured logging

`KP-Capture` is the only log tag this phase writes to, and only ever carries task ids,
lifecycle-state names, byte counts, and error categories (e.g. `begin_capture task=T1
result=started ceilingBytes=15728640`, `finalize_capture task=T1 result=failed
category=promote_error`) — never a file path, never media bytes, never the database
passphrase, never personal information. Emitted from `CaptureScreen.kt` (permission/camera-bind
outcomes) and `EvidenceRepository.kt` (capture/finalize/reconcile outcomes).

## Real bugs found and fixed while building this

Two genuine issues surfaced while getting this green — recorded honestly, not polished away.

**1. `LocalizedApp`'s locale-switch `CompositionLocalProvider` silently broke
`BackHandler`/`rememberLauncherForActivityResult` for every screen beneath it.**
`Context.createConfigurationContext()` (used to apply the in-app language override) returns a
standalone `Context` that does **not** wrap the original `Activity` in its `ContextWrapper`
chain. `androidx.activity`'s `LocalOnBackPressedDispatcherOwner` and
`LocalActivityResultRegistryOwner` resolve their default value by unwrapping
`LocalContext.current` looking for the `Activity` — so overriding `LocalContext` for the
locale switch (present since P3, but never exercised by anything needing those two locals
until P4's `CaptureScreen` added `rememberLauncherForActivityResult` for the camera/mic
permission launcher and `BackHandler` for safe capture cancellation) made both throw
`IllegalStateException` the moment a user — or an instrumented test — reached the capture
screen. Confirmed on the real device, not just in tests: a manually-installed build crashed
identically.

Fixed by resolving both owners from the real, pre-override ambient composition **before**
overriding `LocalContext`, then re-providing them explicitly alongside the locale override
(`MainActivity.kt`'s `LocalizedApp`). This is a genuine pre-existing landmine in the P3 code
that P4 was the first feature to actually step on — not a new defect introduced by sloppy P4
code, but also not something P3's own test suite could have caught, since P3 never used either
composition local.

**2. Navigating back after a capture could occasionally crash with `IllegalStateException:
Method setCurrentState must be called on the main thread`.** Caught by
`EvidenceCaptureFlowTest` the first time it actually ran real camera capture against real,
human-granted permissions (see the manual gate below for how that permission got granted —
unattended/scripted granting is blocked on this test device, so this code path had not been
exercised by an automated run before that point). The real stack trace pinned the exact cause:
`EvidenceRepository.finalizeCapture()`'s Room suspend calls run through Room's own
`TransactionExecutor` thread pool, and the calling coroutine resumed on *that* thread rather
than hopping back to Main before calling `onDone()` → `NavController.popBackStack()`, which
Jetpack Navigation enforces must run on the main thread. `withContext` is supposed to always
return execution to the original calling dispatcher, and it reliably does under real
`Dispatchers.Main` — this is narrowly about Compose UI Test's own frame-deferring continuation
interceptor (visible in the stack trace: `ApplyingContinuationInterceptor`,
`FrameDeferringContinuationInterceptor`) not perfectly preserving that guarantee through a
nested Room dispatcher hop, so there's a real possibility this was test-harness-only and never
reachable in actual production use (consistent with zero crashes across the many real
capture/replace/retake/delete cycles the human tester performed in the manual gate, both
before and after this fix). Regardless of whether it was production-reachable, the fix is
unambiguously correct defensive practice either way.

Fixed in both places this pattern appears — `CaptureScreen.kt` (after a successful
finalize) and `EvidencePreviewScreen.kt` (after a confirmed delete) — by explicitly wrapping
the post-suspend navigation callback in `withContext(Dispatchers.Main.immediate) { onDone() }`
/ `{ onDeleted() }`, which guarantees the call lands on the main thread regardless of which
thread the preceding suspend call happened to resume on. Verified fixed: `assembleDebug`,
`lintDebug`, `testDebugUnitTest`, and `connectedDebugAndroidTest` all green afterward (see
below); `EvidenceCaptureFlowTest`'s real-capture path could not be re-exercised a second time
in the same automated run because the OS re-revoked the test's unattended permission grant
between runs (the same OEM restriction documented below) — but the identical
capture→finalize→navigate and delete→navigate code paths were also exercised repeatedly and
successfully by the human tester in the manual gate.

## Limits, stated honestly

- Declaration/consent/registration and the live match computation remain in-memory,
  ViewModel-scoped only (unchanged from P3) — only evidence capture is durable in P4. A
  resumed draft returns straight to the task list; re-running the declaration is not possible
  without starting a fresh draft (delete the current one first).
- `EvidenceCaptureFlowTest`'s own real-camera roundtrip is currently unattended-skipped on
  this specific OEM build for the documented reason above; it is not disabled, deleted, or
  marked `@Ignore` — it will run for real on any environment where runtime permission granting
  actually works (most devices/emulators/CI do not have this specific OEM restriction).
- The exact byte-boundary budget-overflow scenario (fill a task's budget to the exact byte,
  assert rejection) is proven at the unit level only, against synthetic data for the
  total-budget-but-not-task-budget case — a real captured photo/video's size can't be dialled
  to an exact number the way P3's old mock slider could, so this is a deliberate, honest shift
  in *where* that exact-boundary proof lives, not a loss of coverage.
- CI (`.github/workflows/ci.yml`) does not run `connectedDebugAndroidTest` — unchanged
  constraint from P3 (documented there as a GitHub-hosted-runner nested-virtualization
  limitation); the instrumented suite is run locally/on-device only, exactly as reproduced
  above.
- Debug-only `P4_TEST_ONLY` ceiling: present in the debug build only, verified baked out of
  release as a compile-time constant — but this project currently has no signing config for a
  genuine release build; `verifyP4TestCeilingDisabledInRelease` checks the generated
  `BuildConfig` for the release variant, which does not require signing.
- Video safety-ceiling enforcement (debug test ceiling and the real per-task/total budgets
  alike) stops recording the first status tick *at or after* the limit is reached, not at the
  exact byte — observed on real hardware as a small, bounded overshoot (~24–30 KB past a 4 MB
  ceiling in the manual gate, ~0.6–0.7%). This is inherent to any live-byte-monitored stop
  mechanism and is not unbounded; a task or the assessment total can therefore end up a few
  tens of KB over its nominal budget after the *single* capture that fills it, but no further
  capture is ever accepted once the remaining budget reaches zero.
- A P4_TEST_ONLY draft the user asked to keep on-device for demonstration was later lost as an
  unintended side effect of re-running the full instrumented suite after the manual gate had
  already passed (`connectedDebugAndroidTest` uninstalls the app when it finishes, wiping
  app-private data along with it). This was a process mistake, disclosed directly to the user
  at the time, made after the gate's own evidence (screenshots, `run-as` file listings, DB
  state) had already been fully captured — it does not affect the validity of the gate result
  above, only the on-device demo artifact.
