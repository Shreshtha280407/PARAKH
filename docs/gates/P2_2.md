# P2.2 completion gate

Branch: `feature/p2.1` (continued). Date: 2026-10-10. Builds on P2.1
(`docs/gates/P2_1.md`, whose checks all still pass — see section 10).
Every item below has a command you can run yourself; "Expected" is the
literal output/exit code; "Manual"/"Live verification" notes anything that
also needed a human (or a real browser) to look at; "Limitations" is what's
honestly still missing.

## 0. P2.1 audit fixes

### 0A — Concurrency-safe upload reservation

- **Command**: `TEST_DATABASE_URL=postgresql+psycopg://parakh:parakh_test_pw@localhost:5432/parakh_test python -m pytest server/tests/test_uploads.py -k concurrent -v`
- **Expected**: PASS, including
  `test_concurrent_reservations_on_same_task_never_jointly_exceed_its_budget`
  -- two real threads, two independent DB connections, two simultaneous 10
  MB reservation attempts on T1 (15 MB budget): exactly one 201, exactly
  one 409.
- **Fix**: `routers/uploads.py::open_upload_session` now takes
  `SELECT ... FOR UPDATE` on the `assessments` row (not just the task,
  since the 120 MB total budget spans all five tasks) before calling
  `quota.check_quota` and inserting the `UploadSession`, all in the one
  transaction that the `db.commit()` closes.
- **Verified the test actually catches the bug**: the lock line was
  temporarily removed and the test was confirmed to fail reliably (both
  reservations succeeded) three runs in a row, then restored and reverified
  green -- not just "a test that happens to pass."
- **Docs corrected**: `docs/gates/P2_1.md` section C3 no longer claims the
  P2.1-era sequential test proved concurrency; it now explicitly says what
  it did and didn't prove, and points here.

### 0B — Concurrency-safe chunk/complete mutations

- **Command**: same file, `-k "chunk_puts or complete_calls"`.
- **Expected**: PASS --
  `test_concurrent_identical_chunk_puts_never_double_append` and
  `test_concurrent_complete_calls_never_create_two_evidence_items`, each a
  real two-thread/two-connection proof.
- **Fix**: `_require_worker_token_for_session(..., lock=True)` now does
  `db.get(UploadSession, id, with_for_update=True)` before `put_chunk`/
  `complete_upload` mutate anything. Without the lock, both tests fail
  reliably (confirmed the same way as 0A): two concurrent identical-chunk
  PUTs both append to the storage file before either's DB commit is
  visible to the other (the append happens outside the DB transaction, so
  even the "losing" request's bytes land on disk); two concurrent
  completes both see `status="open"` and both create an `EvidenceItem`.
  With the lock, the second request blocks, then (seeing the first's now-
  committed state) correctly takes the idempotent-replay path instead.

### 0C — Atomic evidence finalisation + job creation

- **Command**: `python -m pytest server/tests/test_uploads.py -k atomic -v`
- **Expected**: PASS --
  `test_evidence_finalisation_and_job_creation_are_atomic` monkeypatches

## 4. Tamper-evident signed reports

- **Command**: `python -m pytest server/tests/test_reports.py server/tests/test_config.py -v`
- **Expected**: `test_reports.py` 10/10, `test_config.py` 8/8.
- **Signing**: `server/app/report_signing.py`, Ed25519
  (`cryptography.hazmat.primitives.asymmetric.ed25519`). A canonical JSON
  snapshot (`json.dumps(..., sort_keys=True, separators=(",", ":"))`) is
  SHA-256 hashed and the hash is signed; `SignedReport` stores the literal
  `canonical_json` + `sha256` + `signature` + `key_id`, not a re-derivable
  summary -- so tampering with any of those three fields independently
  (not just the underlying rows) is detectable.
- **`POST /assessments/{id}/report`**: assessor/admin only, only once a
  decision exists (`recommended`/`needs_reassessment`, 409 otherwise);
  idempotent -- calling it again returns the exact same signed artifact,
  never resigns.
- **`GET /reports/{id}/verify`**: **public, no auth at all** -- the whole
  point of signing is third-party verifiability. Re-derives the hash from
  the stored `canonical_json` and checks it against the stored `sha256`,
  then verifies the Ed25519 signature against this server's current
  public key (derived from the private key, no separate public-key
  setting to keep in sync). Returns only `{valid, assessment_id, key_id,
  signed_at}` -- **never** the report content, scores, or any evidence.
- **The actual tamper test**:
  `test_verify_detects_tampering_with_the_stored_report` directly mutates
  the stored `canonical_json` in the DB (simulating an attacker with
  write access editing a score after the fact) and confirms
  `GET /reports/{id}/verify` flips from `valid: true` to `valid: false`.
- **Download**: `GET /assessments/{id}/report?format=json|pdf`, same dual
  auth as `GET /assessments/{id}` (assessor/admin JWT or the assessment's
  own worker token). PDF via `reportlab` (pure-Python, no system
  dependency like WeasyPrint's pango/cairo) -- `test_download_report_pdf`
  checks the real `%PDF` magic bytes.
- **Key management, env-based with fail-fast**: `REPORT_SIGNING_PRIVATE_KEY`
  (hex 32-byte Ed25519 seed). If unset **and** `APP_ENV=development`, an
  ephemeral key is auto-generated at process start (fine for a local
  demo -- reports signed by a previous run simply won't re-verify).
  Outside development, unset **refuses to start** (`pydantic.ValidationError`
  at `Settings()` construction) -- `test_production_without_a_signing_key_fails_fast`
  / `test_staging_without_a_signing_key_fails_fast`.

## 5. Evidence content/thumbnail serving

- **Command**: `python -m pytest server/tests/test_evidence_serving.py server/tests/test_worker.py -v`
- **Expected**: `test_evidence_serving.py` 6/6, `test_worker.py` 10/10
  (4 new thumbnail-job tests among them).
- **`GET /assessments/{id}/evidence/{eid}/content`**: dual auth (same
  pattern as the assessment detail endpoint), serves the real stored
  bytes via Starlette's `FileResponse`, which implements RFC 7233 Range
  requests **natively** -- no hand-rolled Range parsing was written or is
  needed for video scrubbing.
- **`GET /assessments/{id}/evidence/{eid}/thumbnail`**: photos serve their
  own bytes directly (no job, no extra storage). Videos serve an
  ffmpeg-extracted frame once the background job completes; while queued,
  or if extraction failed/ffmpeg is unavailable, this is a **graceful
  404** (`{"detail": "no thumbnail available (status: ...)"}`, never a
  500) carrying the actual `thumbnail_status` so the dashboard can show a
  pending state.
- **Background job**: `generate_thumbnail`, enqueued alongside
  `verify_evidence` (same atomic transaction, section 0C) whenever
  completed evidence is a video. `worker.py::_generate_thumbnail` shells
  out to real `ffmpeg` (`-ss 00:00:00.5 -frames:v 1`); missing ffmpeg, a
  timeout, or a corrupt video all land on `thumbnail_status = "unavailable"`
  **without raising** (not a retryable failure -- these are expected,
  permanent outcomes, and the original evidence must stay servable either
  way). `test_generate_thumbnail_extracts_a_real_frame_from_a_real_video`
  synthesizes a real tiny MP4 with ffmpeg's `lavfi` test source (no
  external fixture file) and asserts the output is real JPEG bytes
  (`\xff\xd8\xff` magic).
- **Deliberately NOT CV/AI inference anywhere in this section** -- pure
  frame extraction for a UI preview. See section 6 (EvidenceQualityResult)
  for the explicitly-no-model-exists contract this leaves room for later.
- **Live-verified against the real Docker image**: `server/Dockerfile` now
  installs `ffmpeg` (shared by `api`/`migrate`/`worker`, one apt layer);
  uploaded a real synthetic video through the actual running
  `docker-compose` stack and confirmed `GET .../thumbnail` returned a
  real 320x320 JPEG (not a mock, not `unavailable`) within a few seconds
  of upload.

## 8. Cookie-based dashboard sessions + CSRF

- **Command**: `python -m pytest server/tests/test_auth.py -v`
- **Expected**: 15/15 pass (7 new cookie/CSRF tests among them).
- **Login**: `POST /auth/login` now **also** sets two cookies alongside
  its existing JSON body (kept for API clients/scripts/CI that don't want
  cookie-jar handling): `access_token` (HttpOnly, `SameSite=Lax`, `Secure`
  outside development) and `csrf_token` (readable by JS -- the dashboard
  echoes it back, double-submit pattern).
- **`auth.get_current_user`**: now accepts either a `Authorization: Bearer`
  header **or** the `access_token` cookie (Bearer takes priority). A
  mutating request (POST/PUT/PATCH/DELETE) authenticated via the cookie
  must also send a matching `X-CSRF-Token` header, or it's rejected (403)
  -- `test_mutating_cookie_request_without_csrf_header_is_rejected` /
  `..._with_wrong_csrf_header_is_rejected` /
  `..._with_correct_csrf_header_succeeds`. Bearer-authenticated requests
  **never** need CSRF (`test_bearer_authenticated_mutating_request_never_needs_csrf`)
  -- a cross-site page can't attach a custom header or a bearer token, only
  a cookie gets sent automatically.
- **`_assessor_or_worker_token`** (the separate dependency used by the
  assessment-detail/evidence/report endpoints) was given the identical
  cookie+CSRF treatment -- see section 0D, found via live browser testing.
- **`POST /auth/logout`**: clears both cookies server-side. Required now
  that the cookie is HttpOnly -- the dashboard's JS literally cannot clear
  it itself.
- **Dashboard**: `apps/dashboard/src/auth.ts` (the old `sessionStorage`
  wrapper) is deleted entirely. `api.ts`'s `request()` always sends
  `credentials: "include"` and attaches `X-CSRF-Token` (read from
  `document.cookie`) on every mutating call. `LoginPage`/`App.tsx` no
  longer touch any token directly.
- **CORS**: `allow_credentials=True` (was `False`) -- required for the
  browser to actually send/receive cookies cross-origin. `cors_allow_origins`
  default changed from `"*"` to `"http://localhost:5173"`, and `"*"` is
  now **rejected at startup** (browsers refuse wildcard-origin +
  credentials combinations outright) -- `test_wildcard_cors_origin_always_fails_fast_even_in_development`.

## 10. Background-job crash recovery

- **Command**: `python -m pytest server/tests/test_jobs.py -k recover -v`
- **Expected**: 3/3 pass.
- **Lease**: `Job.lease_expires_at`, set to `now + JOB_LEASE_SECONDS`
  (default 300s) every time `claim_job` claims a row.
- **`jobs.recover_stale_jobs(db)`**: sweeps jobs stuck in `"running"` past
  their lease -- presumed to belong to a worker that was killed or
  crashed before calling `mark_succeeded`/`mark_failed`. Treated exactly
  like a failed attempt: requeued if `attempts < max_attempts`
  (`test_recover_stale_jobs_requeues_a_crashed_workers_job`), permanently
  `failed` otherwise (`test_recover_stale_jobs_fails_permanently_once_attempts_are_exhausted`).
  Row-locks each candidate (`FOR UPDATE SKIP LOCKED`) so two worker
  processes sweeping at the same instant can't double-recover the same
  job. A no-op in the normal case
  (`test_recover_stale_jobs_is_a_no_op_when_nothing_is_stale`).
- **Wired into**: `worker.py`'s `main()` loop calls it once per poll
  cycle, before `run_once` -- no separate cron/process needed, matching
  the existing "a few jobs a minute, no Redis/Celery" scale philosophy.

## Known, stated limitations (carried forward openly)

1. Worker capability tokens still have no **expiry** or device-loss
   **recovery** flow -- rotation/revocation (section 7) close part of
   P2.1's stated gap, not all of it; see
   `docs/worker_capability_tokens.md`.
2. No CV/AI inference anywhere -- `quality_check_status` (section 6) and
   thumbnail extraction (section 5) are both explicitly non-ML. `EvidenceQualityResult`
   remains a documented contract with nothing behind it.
3. `JOB_LEASE_SECONDS` crash recovery (section 10) assumes a single
   worker process in practice (the MVP's actual deployment shape); the
   `SKIP LOCKED` sweep is correct under multiple workers too, but that
   configuration has not been exercised live.
4. Report PDFs (`reportlab`) are intentionally plain -- a real printable
   certificate-style layout was out of scope; the content is complete and
   correct, the typesetting is not polished.
5. The dashboard remains intentionally basic/functional (see P2.1's
   stated scope) -- the new scoring/report/token panels follow the same
   plain-CSS, no-component-library approach, not a redesign.
6. `CON/N0603.PC16` (diesel generator maintenance) remains
   `NOT_APPLICABLE_IN_MVP` from P1.1 -- untouched by this branch, carried
   forward as-is.
